# Armor lane report: a first long-run soak (measurement only)

- **Date:** 2026-10-10. **Lane:** Blind-Spot Armor risk row 5, long-run drift (`docs/strategy/blind-spot-armor.md`; ADR-197).
- **Authority:** the lead's overnight brief, with the human's "Go" on the B448 batch. Measurement only: no source or tool file was changed. The only files added are this report and `traces/2026-10-10-armor-soak-first.md`. `docs/armor/catalogue.json` and `dashboard.html` are the lead's and were not touched.
- **Built from:** `4a3dbaf5e45407590f18ed7cebd2c5ae1e81bc05` (origin/main at the start of the run), Release (`-O3`), Apple Silicon, Command Line Tools. The PR commit adds only docs on top of that hash, so every number below is the tools at that hash.
- **Status:** the first soak ran. Everything that exists passed. The finding is about what the existing tools can not see, listed in section 4.

## 1. Result in one paragraph

`tools/stability_check` was run at 60, 600, 3600 and 14400 simulated seconds (4 hours) on its fixed nine-patch list. All five bars passed at all four durations. No non-finite sample, no RMS walk (worst 10-second-window drift 0.25 dB against a 1.0 dB bar, and it does not grow with duration), the peak never left the output tanh's bound. Two running maxima (peak and the coupling smoother) crept up by small amounts between 60 s and 3600 s and then stopped. That passes row 5 only for what the tool measures. Row 5 asks for **per engine**, **level, DC and spectral centroid**, at **extreme settings**, and for 4 hours. The legacy SAW core is the only engine measured; DC and centroid are not measured at all; horde 2's composed engine has no long-run measurement of any kind. The tool also holds the entire default render in memory, so a 4-hour run needs about 10 GB (section 5).

## 2. What `tools/stability_check.cpp` is (read first)

- **Flags:** one, `--seconds=N` (minimum 25). No flag selects a patch, a setting, a seed, a block size or a sample rate. The seed (1234), the 128-frame block, 44.1 kHz and the three held notes (60, 64, 67; one voice's state is read) are constants in the source.
- **Configurations:** a fixed list of nine patches in `main()`. So there is no way to ask for "maximum coupling", "maximum voices" and so on from the command line; the list is what the source says. It already contains several extremes: K = 1, K = -1, inertia 0.95 with K = 1, ring topology with reach 5, two-cluster with K = -1, drift depth 100, gravity with basin 60, and an "everything" patch (n 16, oversample, drift, gravity, pan motion, glide). It does **not** reach the engine's ceilings where I checked: `kMaxV` is 32 (`src/swarm_core.h:41`) and the densest patch uses n = 16. The absence of flags is itself a finding.
- **Five measured quantities:** RMS drift (first 10 s window vs last 10 s window, dB, left channel only), f0 drift (lowest gated voice's `f0cur` at t = 10 s vs the end, cents), peak (running max over the whole run), max |Ksm| (running max of the coupling smoother), non-finite count.
- **Start / mid / end:** the tool reports only the first window, the last window and run-wide maxima. It has no mid-run sample. This report reconstructs the trajectory differently: the render is deterministic (fixed seed, fixed notes), so a 60 s run is a prefix of the 14400 s run. The "RMSn" column at 60 / 600 / 3600 / 14400 s is therefore four points of one trajectory, the 10-second window ending at each duration. Evidence that the runs really are prefixes: the first-window column (RMS0) is identical across all four runs, and the running maxima never decrease with duration.
- **Controls:** the scorer has three must-fail plants (a +3 dB ramp, one NaN, one over-unity sample) and one must-read-clean. All four passed at every duration; the +3 dB plant read 2.52, 2.97, 3.03 and 3.02 dB of drift at 60, 600, 3600 and 14400 s, so the RMS column can fail. **There is no plant for the f0 column or the Ksm column** (see 4b).

## 4. Trends, and what the numbers do and do not say

**a. No time trend in level.** Across 60 s to 4 h no patch's last-window RMS moves monotonically. The two patches with the largest drift (`drift 1 walk`, `inertia 0.95 + K1`) go 0.22, 0.13, 0.05, 0.24 dB and 0.14, 0.12, 0.12, 0.23 dB: up, down, up. That is the sampling scatter of a 10-second window on a stochastic or slowly wandering system (about 0.1 to 0.25 dB), not a slope. The stiff patches (K 1, ring, two-cluster, K -1) hold within 0.02 dB for 4 hours. Reading: the 1.0 dB bar is about four times the observed scatter, which is a sensible margin, and a real walk of the size the bar exists for would need to show up as a monotone series.

**b. The f0 column reads exactly 0.000 on every patch at every duration, including `drift 1 walk`.** The metric is `f0cur` of the lowest gated voice, a control-rate pitch target moved by glide and the gravity pull (`src/swarm_core.h:569-626`, `:838`), and it is baselined at t = 10 s after settling. It does not move under the drift random walk, so it is a *reads-zero* metric, and unlike RMS, NaN and peak it has **no must-fail plant** among the four controls. The audit's own number was 0.001 ct, i.e. already at the probe's resolution. So "f0 drift 0.000 over 4 h" should be read as "the note-frequency target did not move", not "the audible pitch did not move". This is the doctrine's detector-shares-assumption trap and it should be closed with a plant before anyone cites it. (Hypothesis, not tested here: I did not plant a fault in the f0 reading; I read the code and the zero.)

**c. Two running maxima crept, then stopped.** Peak on `K 1 locked` and `ring` rose by 0.002 over 60 s to 14400 s, and Ksm on `everything` rose 17.80 to 19.63. The increments shrink (Ksm: +1.17 between 60 and 600 s, +0.67 between 600 and 3600 s, 0 between 3600 and 14400 s). A running maximum of a stationary random process behaves like this; a divergence would not saturate. The worst values sit 0.18 under the peak bar and 10 times under the Ksm bar. Not a finding against the engine; recorded because the series is the only slope this data gives.

**d. Window-to-window scatter is the real noise floor.** Any future bound on RMS drift should be set against 0.25 dB of scatter, not against zero. Below about 0.5 dB a fixed-window comparison cannot tell a slow walk from noise; that argues for a regression slope over many windows (section 6), not for a tighter first-vs-last bar.

**e. No failure.** No bar failed, no non-finite sample appeared, no run diverged. Nothing was retried.

## 5. Cost and a defect-in-waiting in the tool

- `stability_check` keeps every sample of the default patch's render (`std::vector<float> keep`) for its controls, then copies it three times for the plants. At 14400 s that is 2.5 GB of floats, and the 4-hour run reached 6.7 GB resident and a 10.2 GB peak footprint on a 24 GB machine. 3600 s needs 2.0 GB resident. A CI runner with less than about 12 GB would not complete a 4-hour run of this tool as written (I did not check what the hosted runners offer). This is a property to design out of the real gate (streaming accumulators), not a bug in the 60 s `verify full` use.
- Its stdout is block-buffered when redirected, so a run killed for memory would lose the whole table. I ran the long jobs under a pseudo-terminal to keep it line-buffered and read progress.
- Its bar messages say "over ten minutes" at every duration (the strings are fixed), so a 4-hour PASS line reads "RMS does not drift over ten minutes". Cosmetic, but a pasted log would mislead.

## 7. Proposal for the real soak gate (proposal only; nothing built)

**Tool.** One new `tools/soak_check.cpp` (Layer-E: measured and reported, not CI-blocking, with the guaranteed-versus-measured distinction stated in its output). It drives each engine behind a small adapter so the metrics code is shared: the legacy `SwarmCore`, and horde 2's `horde2::engine::Engine` (it is already driven by `measure_h2_engine.cpp:runCell`, 8 voices per engine). Seed fixed, block 128, 44.1 kHz, deterministic.

**Streaming, not buffering.** Accumulate per window (propose 10 simulated minutes, 24 windows for 4 h) and keep only the window summaries. This removes the 10 GB footprint and lets a CI runner finish.

**Per window and per channel, report and bound:**

| metric | how | proposed bound (to be calibrated on the first run of the new tool) |
|---|---|---|
| level | RMS dBFS | every window within 1.0 dB of window 0 (this checks the middle, which today's tool can not), and the least-squares slope across windows magnitude at most 0.1 dB per hour. Rationale: the scatter measured here is up to 0.25 dB per 10 s window; with 10-minute windows it will be far smaller, so 1.0 dB stays safe |
| DC | window mean | magnitude at most 1e-3 (-60 dBFS) per channel, and slope bound. Unmeasured today: the number is a placeholder to be set from a baseline, with a must-fail plant |
| spectral centroid | Hann 4096-point frames, power-weighted mean frequency, averaged over the window | within a stated percentage of window 0 (propose a starting 5 %, to be replaced by twice the baseline's measured scatter) |
| peak | window max | at most 1.0 (the tanh bound) and non-decreasing excursions reported |
| non-finite, subnormal | counts | 0 and 0 |
| engine state | one reading per engine (legacy: max abs Ksm; horde 2: its load readouts culled / refused / stolen) | divergence bar as today (200 for Ksm); the readouts reported, not gated |

**Configurations (extreme settings).** Owned by the tool as data, not hard-coded in `main`: the nine existing patches, plus n = 32, `superMode` 3 with width 1.3, oversample on, and for horde 2 the ledger's seven presets (`docs/port/cpu-ledger.md`) at 8 and 16 voices and both oversampling settings, plus defaults. Each configuration runs once held and once with a deterministic note-churn script (retrigger, steal, bend every simulated minute).

**Controls (L0032).** A must-fail plant for every metric, applied to the window summaries: a slow gain ramp (level), a small linear offset (DC), a slow low-pass (centroid), a planted NaN, a planted subnormal, and a plant that moves the f0 reading so that column can read non-zero (section 4b). Plus a must-read-clean on the unplanted render.

**Where it runs.** Nightly on `main` in GitHub Actions, one matrix leg per configuration, not in `verify fast` or `verify full` (human-paced and macOS-local per the charter). The armor law already says that 4 hours fits the 6-hour job limit (`docs/strategy/blind-spot-armor.md`, the soak line). Cost, from this report: the legacy nine patches are 31 minutes of wall time on this loaded machine, so each patch as its own leg is a few minutes; horde 2 at 8 voices ran 4 hours in 1780 s (30 minutes; the 3600 s run took 609 s because the machine was busier), so about 30 to 40 minutes per configuration here. `./verify full` keeps `stability_check --seconds=60` as the smoke. A short mode of the new tool (`--seconds`) would stand in for the `full` smoke. The dashboard cell should read "Soak 4h: pass" only from a dated nightly artifact, never from a local run.

**What the lead decides:** the home of the real bars (a first calibration run of the new tool; I did not guess DC or centroid numbers), whether row 5's cell stays PARTIAL until horde 2 is in the tool, and whether GitHub-hosted macOS runners are acceptable for a libm-sensitive soak (the bounds are tolerances, not digests, so a Linux runner would also work; the digests would not be comparable).

## 9. Reproduction

From a clean checkout at `4a3dbaf5e45407590f18ed7cebd2c5ae1e81bc05`. Absolute build paths (the sandbox resets cwd). `<repo>` is the checkout.

```
git submodule update --init --recursive
git switch -c armor-soak-first origin/main
cmake -S <repo> -B <repo>/build-release -G "Unix Makefiles" -DCMAKE_BUILD_TYPE=Release
cmake --build <repo>/build-release -j8 --target stability_check denormal_check sr_check blocksize_check measure_h2_engine

# the four durations (each prints the same table; run long ones in the background)
<repo>/build-release/stability_check --seconds=60
<repo>/build-release/stability_check --seconds=600
<repo>/build-release/stability_check --seconds=3600
# 4 h: needs about 10 GB; under script(1) so stdout stays line-buffered and progress is readable
script -q <log> /usr/bin/time -l <repo>/build-release/stability_check --seconds=14400

# horde 2 (run from the repo root: it renders the preset stream with node)
<repo>/build-release/measure_h2_engine --hold defaults 8 3600
<repo>/build-release/measure_h2_engine --hold defaults 8 14400

# the seconds-scale tools
<repo>/build-release/denormal_check
<repo>/build-release/sr_check
<repo>/build-release/blocksize_check
```

The runs are deterministic (fixed seed 1234 and the fixed three notes), so the metric columns reproduce exactly on this toolchain; wall times will not.

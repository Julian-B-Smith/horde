## 3. The clamp, and what PA-7 does and doesn't cover

PA-7 already clamps a host value out of range and counts it, but a host value is v in [0, 1] (IF-11), and every v
maps to 1..9 under the new step count, so **a host can never send "above 9"**. A count above 9 can arrive only in
count form: a bank preset's `N` (B.1) and a version-0 state, which takes B.1's keys (B.2). B.1's `N` said "as is";
it now says "as is, clamped to 1..9 (a clamp is reported)", the wording B.2 already uses for `octave`, `semi` and
`fine`. **Flag:** that sentence is new, minimal, and follows B.2's precedent; whether B.1's "reported" also means
PA-7's counter is not stated, as it isn't for B.2's clamps.

**Flag for the lead and the human: a stored v changes meaning.** Every state of version 1 and every host session
stores `unison` as v. On 1..16, v = 0.4 was 7 members; on 1..9 it is round(0.4 · 8) = 3, so **4 members**; 11
members (v = 0.6667) becomes 6. The manifest is frozen only from the first release (5.1), so RC-9.4's version rise
and migration do not apply to the engine; nothing released holds the old scale. **The test plug-in's own saved Live
sessions from build 9 do:** reopened on a build with the new engine, each saved unison re-reads on the new scale
(and a session saved at the old default 7 opens at 4). Whether the test plug-in migrates its chunk (its own version
number) or the human accepts the shift is a ruling for ADR-381; nothing in this round decides it.

## 4. Committed fixtures (re-recording is the human's gate)

Neither fixture changes in this commit, because both are recorded from the engine, not generated from the spec,
and `tools/engine-preview/build.sh` compares a fresh dump only when the fixture names the same engine commit. They
**will** need re-recording once the builder's engine takes 1..9:

- `tools/labharness/fixtures/gui3-display.json`: the unison rows' five samples become options "1, 3, 5, 7, 9".
- `tools/labharness/fixtures/gui3-replay.json`: its frames carry `osc2.unison` v 0.4; until re-recorded, the page
  replaying it shows 4 members where the engine that recorded it played 7. The replay also carries the engine's
  manifest hash; the page's is now `2cf4a525…` and a bridge on the old engine reports a **mismatch** banner naming
  `osc1.unison` and `osc2.unison` until the engine is rebuilt.

## 5. For the builder (the lead sends)

- `unison`'s row: 1..9, default 7, 9 steps; the manifest's lockfile entry for `osc1.unison` and `osc2.unison`
  (IF-11: id, key, min, max, default, taper, steps) changes `max` 16 → 9 and `steps` 16 → 9. **This is a re-ranged
  id**, which IF-11's lockfile and RC-9.1 treat as append-only; it needs the human's approval recorded as ADR-381
  before the builder's lock check will accept it.
- `kMaxMembers` (and every buffer RT-1 sizes by it) → 9.
- C.8's balanced image: the U = 10..16 branch is gone.
- PF-7's worst-case memory **should drop** (members are now 9 of 16 per voice and oscillator); the builder measures
  and states the new figure in the manifest.
- B.1's `N` is clamped to 9 with the clamp reported (no bank preset reaches it).

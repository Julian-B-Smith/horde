Provenance colouring (human request 2026-08-05 — the reason this page needs the morph vocabulary)

With the morph parked at an intermediate position, every parameter is showing a value that came from somewhere, and today the page gives you no way to know where. So each control wears the hue and glyph of the corner its live value came from — glyph as well as hue, because colour alone fails for colour-blind users and in screenshots. Where corners blend rather than one winning, the chip is hatched neutral: honest about there being no single source. The vocabulary is identical to the mod lab's (◆ GLASS · ▲ GRIT · ● HOLLOW · ■ BLOOM), per the standing convention that corner colour means one thing everywhere.

Decision 2 — the multi-oscillator architecture (ANSWERED — ADR-082 ratified 2026-08-06: 2 slots; increment 1 shipped inert)

Answered as a proposal 2026-08-06 (ADR-082). Id scheme: id(P, osc k) = id(P, osc 0) + 100k — osc 0 keeps every id it has, so all existing sessions and automation survive; osc 1 takes 100–199, osc 2 takes 200–299, and the gaps where a global's id would fall are left permanently unallocated as self-documentation. Measured basis: 99 params, ids 1–99 with no gaps, ~70 of them per-oscillator. CPU falls out as a real constraint — at the project's own ×4 min-spec derate, 3 oscillators and 2× oversampling reaches ~75% against a 50% budget, so those two cannot both be unconditional. Rejected: re-homing ids into clean blocks (impossible, append-only) and a single param set with an edit-target selector (kills per-osc automation). Superseded text follows.
Today: ONE engine select + A/B balance + sub. The brief asks for 2–3 full oscillators, each independently SAW/SPECTRA/…. That is not a GUI change — it is N core instances with per-osc params, per-osc state, doubled CPU, and a param-id namespace design (per-osc id blocks? osc-index modifier?). Ids are append-only, so this must be designed ONCE, correctly. Recommendation: ADR first (id scheme + voice/CPU budget + per-osc preset format), then a thin 2-osc walking skeleton behind the existing balance param, then the GUI.

Decision 5 — three preset tiers (human 2026-08-06)

Global · morph corner · oscillator. The bottom tier is nearly free already: ADR-082 gives every per-oscillator param the state key o<k>.name, so an oscillator preset is exactly the subset of state keys carrying one prefix — saving one is a filter, loading it into another slot is a prefix rewrite, and "copy osc 1 → osc 2" needs no new format at all. That was not designed for presets; it falls out of the id scheme, which is a good sign the scheme is the right shape.

The corner tier needs a ruling first. A morph corner holds a value for every parameter it owns — but which parameters? Two readings, and they are not interchangeable:
  (a) corners are global — one corner spans both oscillators, so a corner preset is a whole-instrument snapshot minus the globals. Four corner-sets total. Simple; a corner cannot morph the oscillators independently.
  (b) corners are per-oscillator — each oscillator owns its own four corners, so corner × oscillator is a 2×4 grid of value sets. Far more expressive (osc 1 morphs while osc 2 holds), and doubles the authoring surface plus every "which corner am I editing" affordance.

Ask (a)/(b) before building either, because the preset FORMAT differs: under (a) a corner preset contains per-osc blocks; under (b) it belongs inside one. Getting this backwards means rewriting saved presets, which is the one thing a preset format may not do.

Also open: what a global preset does to per-corner mod depths (A10 gave every morph-owned matrix cell four), and whether an oscillator preset carries its corner values with it or lands flat into the current corner.

# b350-thresh-v2 — the human's ruled listening-pass cuts applied to gauntlet.mjs THRESH

- **Queue item:** B350. Read verbatim from `origin/lead-records-140:ROADMAP.md` (records PR #845),
  beside B344 and B345. The human, on the lead's recommendation from B345's re-fit: "I think I'm
  comfortable with it".
- **Why:** B344/B345 fitted four cuts against 34 blind ratings on the worst-heard segment; B350 is
  the human's ruling to apply them. THRESH changes only by a recorded human decision (charter,
  gauntlet.mjs header) — this is that decision, applied nowhere else.

## What changed

- `tools/patchspace/gauntlet.mjs`: `THRESH.aliasDb` −30 → −26.8, `THRESH.roughness` 0.10 → 0.12,
  `THRESH.rootPresence` 0.50 → 0.616; `THRESH.flatness` (0.3) removed — the noise gate is now
  `THRESH.noiseDb` (−21.5 dB, the metric B345 added). `incoherence()`'s noisy verdict reads
  `r.noiseDb > THRESH.noiseDb` instead of `r.flatness > THRESH.flatness`; flatness is still
  measured and still printed by `gauntlet_report.mjs`, just no longer a gate.
- `tools/patchspace/gauntlet_report.mjs`: the printed threshold table's `noisy` row now names
  `noiseDb` (was interpolating the now-absent `THRESH.flatness`, which would have printed
  `undefined`).
- `docs/design/listening-pass.html` (the PURE block, `detectorControls()`): the "not noisy" /
  "seeded white noise ... noisy" gates now check `T.noiseDb` when the caller's threshold object
  carries it, falling back to `T.flatness` when it does not — needed because this function is
  called two ways: `listening_pass_check.mjs`'s T10 passes the live `THRESH` (which now has
  `noiseDb`, not `flatness`), while the page's own in-browser self-check passes the committed,
  frozen `SAMPLE.thresholds` (which predates any noise-gate metric and never had `noiseDb`).
  Without the fallback, T10 would compare every "not noisy" assertion (all six steady-note sine
  rows) against `undefined` and fail outright.
- `tools/patchspace/listening_pass_check.mjs`: two pins moved, both **only** because the ruled
  THRESH moved, not because of any metric or logic change:
  - **T1** asserted `sample.thresholds[k] === THRESH[k]` for `aliasDb/roughness/rootPresence/
    flatness`. That equality was true because THRESH had never moved since B316; B350 is the
    first ruled move, and the sample is explicitly NOT regenerated (out of this brief's scope,
    and B345 already re-measured it once without touching `thresholds`). Pinned instead to a new
    `FROZEN_THRESH = { aliasDb: -30, roughness: 0.1, rootPresence: 0.5, flatness: 0.3 }` — the
    B316 values verified still present in the committed `docs/design/listening-pass.json`. The
    check still catches a corrupted/hand-edited `thresholds` field; it no longer requires that
    field to track THRESH forever, which is what B350 makes true by design.
  - **T4** re-derives each item's `roughOrigin` label via `roughOrigin(roughness, solo,
    THRESH.roughness)` and diffs it against the committed label. A live 0.12 would flip the label
    for any item whose roughness sits in [0.10, 0.12) relative to what was labelled at generation
    time (0.10). Pinned to the same `FROZEN_THRESH.roughness`.

## Checked, left unchanged (not live THRESH consumers, or dead code for verify)

- `docs/design/listening-pass.json` (`sample.thresholds`): frozen historical record of what
  THRESH held when this sample was generated/re-measured; per T1's new intent, correctly stays
  `{aliasDb:-30, roughness:0.1, rootPresence:0.5, flatness:0.3}` with no `noiseDb` key (there was
  none to record at that time).
- `tools/patchspace/calibrate.mjs`: its "provisional" columns read `sample.thresholds` (line
  `const T = sample.thresholds;`), never `gauntlet.mjs`'s live `THRESH` — no import of it at all.
  Not a consumer of the live value; nothing to move.
- `tools/patchspace/listening_sample.mjs`: `STRATA`/`CONTROLS` read `THRESH.flatness` etc. at
  module load for stratifying a **new** sample, but are exercised only by `main()` (guarded by
  the `process.argv[1]` check), which no check calls and which this brief does not run
  (regenerating the sample is out of scope). `THRESH.flatness` is now `undefined` there, so a
  future full regeneration would need this file updated too — flagged as an open question below,
  not touched here (editing the generator's banding logic wasn't authorised and isn't exercised).
- `tools/patchspace/metrics.mjs`, `dependency_tree_check.mjs`, `fidelity_scan_check.mjs`: no
  reference to `gauntlet.mjs THRESH` found (checked by grep); confirmed unaffected by running
  both checks green (see Verify).
- `tools/patchspace/README.md`: mentions THRESH only generically, no numeric pins to move.

## Verify

- `node tools/patchspace/metrics_check.mjs` — GREEN, unaffected (does not import THRESH).
- `node tools/patchspace/fidelity_scan_check.mjs` — GREEN, unaffected.
- `node tools/patchspace/dependency_tree_check.mjs` — GREEN, unaffected.
- `./verify fast` — exit 0 at `bb86075`.
- `./verify full` — **exit 1** at `bb86075`, halting at `listening_pass_check.mjs` (fail-fast
  `return 1` in `verify`'s `full()`; every gate after it in the script did not run). 56/58 checks
  passed; the two failures are one root cause:
  - `naive saw E5 vibrato` (a raw, unmistakably-aliased sawtooth with a 30-cent vibrato) measures
    `aliasDb -27.2 dB`. Under the OLD cut (−30) that reads aliased (`-27.2 > -30`); under B350's
    RULED cut (−26.8) it does not (`-27.2 > -26.8` is false, since −27.2 is the more negative of
    the two). This is a detector control asserting a signal that is aliased BY CONSTRUCTION must
    read aliased — it is not a pin I'm authorised to move, and not a bug in this PR's diff (the
    row's comparison code, `m.aliasDb > T.aliasDb`, is untouched; only the RHS constant moved,
    exactly as ROADMAP B350 instructed).
  - **This is not a surprise the brief lacked context for**: B350's own text names it —
    "the aliasing cut is re-fitted once B346's os-convergence estimator lands" — and B346 is
    already the parallel effort on the aliasing estimator. −26.8 is evidently too loose to catch
    this canonical vibrato case; resolving that (moving aliasDb again, or deciding the detector
    control itself needs to change) is B346's territory and the lead/human's call, not something
    this brief authorises me to fix by changing the ruled number or relaxing a detector control.
  - Left as-is per instruction: "NEVER change a pin or tolerance for any other reason, and never
    relax a check." Reported verbatim in the handback.

## Alternatives rejected

- Silently loosening `detectorControls`'s "naive saw E5 vibrato" expectation, or excluding it from
  assertion, to force `verify full` green — rejected: it is a live invariant (a detector-shares-
  assumption control), not a bookkeeping pin, and moving it is a judgment call about whether
  −26.8 is an acceptable aliasDb cut, i.e. exactly the human's decision, not mine.
- Regenerating `docs/design/listening-pass.json` (or editing `listening_sample.mjs`'s STRATA to
  track the new THRESH) to keep everything self-consistent — rejected: explicitly out of scope
  ("do not regenerate the P3 gauntlet or fidelity-audit reports"; regenerating rated listening
  data is the same class of action, and STRATA isn't exercised by verify regardless).

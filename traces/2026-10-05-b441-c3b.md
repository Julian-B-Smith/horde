# b441-c3b — blade 2 and the serial path specialised: 6 kernels and 7 serial orders, bit-identical

- **Queue item:** ROADMAP B441 phase 2, C3b. Lead brief of 2026-10-05 (horde lead session; the human: "Go ahead with blade-2 and serial-path work"; follows C3, #943). The acceptance text is the C3b note on the lead's records branch (`lead-records-191`, local, not yet pushed; the brief quotes it verbatim): "C3b = specialise blade 2 (`mode2`, `hot2`, `b2fm`, blade 2's base and mirror) and `outSerial` within the C3 kernel framework, since they stay generic after C3 and are why Fold over sync, Breathing pad and Crush vs FM gained least. Acceptance as C3: both self-digests 543/543 with no re-pin; parity green; COVERAGE shows every new specialisation reached; a must-fail control that moves only the touched kernel's rows; libm census diff; timing under B441-1/2/3 for the affected presets plus a null control; `./verify fast` and `full` 0. Also: `./verify` echoes the COVERAGE line (an addition, ADR-180 §1)."
- **Why:** after C3 every `+b2` kernel still read blade 2's selectors at run time (`BAny`), and the serial path (`outSerial` → `ev` → `voiceOut`) was the generic, out-of-line one in every kernel, so the patches whose blade 2 or serial interplay carries the work gained least (Fold over sync 1.03–1.06×, Breathing pad 1.10–1.13×, Crush vs FM 1.14×). Blade 2's selectors are as fixed per render call as blade 1's: `fillG2` writes blade 2's view from `s`, which `renderCallK` copies from `d`, at every sample's first step before any member steps (`engine.h` renderCallK, the C1 block).
- **Census first (measure, don't guess).** A scratch build of the parity self-digest (never committed) logged, per render call, the kernel and blade 2's effective selectors (`mode2`, `hot2`, the effective mirror, `b2fm` and the effective `fmType`/`mshape`, `base`, `b2order`) with member steps and serial evaluations, per scenario. The ledger presets: Fold over sync = saw + blade-2 fold (mode2 4), fully serial, blade 2 over; Glass horde pad = phase FM + blade-2 sync on a sine→saw carrier (mode2 0, hot2 6), parallel; Crushed bells = ring + blade-2 crush (mode2 6); Breathing pad = sync + blade-2 **noise** (mode2 3); Crush vs FM = crush + blade-2 phase FM (b2fm 0). (The audit's §1 describes Glass's blade 2 as a fold; the scenario stream says sync, as the C3 trace already did.) Largest blade-2-generic shares left after those: saw + sync (9.6 M member steps), sync + fold (3.9 M), FM + FM (2.4 M).
- **Design (inside the C3 framework, no new mechanism):**
  - Six new kernels `KK<id, B1, 1, B2>` with blade 2 fixed, each checked in `pickKernel` just before its blade-2-generic fallback: saw+fold (11), saw+sync (12), fm+sync (13), ring+crush (14), sync+noise (15), crush+fm (16). Blade-2 descriptors: `B2Fold = BK<4,*,0,*,*>`, `B2Sync = BK<0,*,0,*,*>`, `B2Crush = BK<6,*,0,*,*>`, `B2Noise = BK<3,*,0,*,*>`, and C3's `BFm` reused for blade 2. `fits()` already derived blade 2's view the way `fillG2` does, so no selection logic changed.
  - `BK::scanDead` tightened: a fixed mode that is neither a carrier mode (0, 5, 1, 2) nor a crush (6) proves `scan` dead whatever the carrier (it returns at `if (off < 0) return;` before any read or write). For every C3 kernel the constant is unchanged (BSaw, BCrush, BSync false; BRing, BFm true), so the C3 kernels compile as before on that point.
  - **The serial path:** `outSerial`'s body became `serialK<K, BA, BB>(A, B, …)`, the one serial evaluation, with `evK<K, B>` for `ev`. The generic `outSerial` calls it once with A/B picked at run time (`BAny` both), as before. A kernel specialises the serial path only for the blade orders in its new `Ser` mask (`kSerOver` = b2order 0, blade 2 over; `kSerUnder` = b2order 1); `outK` sends any other order to the generic `outSerial`. Because `b2mix` (serial or not) glides per sample and `b2order` is read per evaluation, neither became a kernel axis: the order is a per-evaluation branch to two typed bodies. The masks are exactly the orders a scenario reaches (measured with every mask full first: 7 of 22 orders reached): saw+b2 over, ring+b2 over, fm+b2 under, saw+fold over and under, saw+sync over, fm+sync over.
  - Coverage: `kernelSerial[id][order]` counts specialised serial evaluations under `H2_ENGINE_KERNELS` (parity build only); `h2_engine_selfdigest_check` prints one `SERIAL` line per specialised order and judges it like a kernel (unreached = RED), and `--kernel-rows` adds `SROWS <id>/<order>`. The judged line is now `PASS  COVERAGE  16 of 16 specialised kernels and 7 of 7 specialised serial orders reached by at least one scenario`. With every mask full the same check read `FAIL  COVERAGE  16 of 16 … and 7 of 22 …` (exit 1): the new half fires.
  - `./verify full` echoes the parity self-digest's `PASS  COVERAGE` line (one grep alternative added; no gate's pass/fail changed; it was always judged by the exit code).

- **Alternatives rejected:**
  - **`b2order` (or serial/parallel) as a kernel axis.** `b2mix` glides per sample, so a call can be partly serial; `b2order` is per call but doubling the kernels for it buys only the branch the per-evaluation dispatch already costs.
  - **Specialising both serial orders in every `+b2` kernel.** 15 of 22 orders would rest on no scenario (measured), which C3's coverage rule calls RED.
  - **A blade-2 axis orthogonal to blade 1 (K × B2).** Multiplicative; the census shows a handful of pairs carry the share.
  - **Fixing `hot2` in B2Sync.** Saw+sync mixes carriers 2/4/6; a per-carrier split triples the sync kernels for a folded switch.

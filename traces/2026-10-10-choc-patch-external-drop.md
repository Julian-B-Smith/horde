# choc-patch-external-drop — a third carried choc patch turns off external drops in the Windows web view

- **Queue item:** B448 Wave C item C3, the Windows follow-up; DECISIONS ADR-205 item 3 (on PR #1022 when this was written). Lead brief of 2026-10-10 (horde lead session). The human approved a third carried choc patch with "go with your recommendations"; that approval covers this change only. The brief cited ADR-205 and the B448 row and carried its own acceptance list; it did not quote ROADMAP text verbatim. I read both records before starting and they agree with the brief (ROADMAP B448: "Windows is not covered natively: WebView2's external-drop switch sits behind a controller choc keeps private, so it needs a third carried choc patch, which is the human's call").
- **Why:** C3 (#1019) made both pages refuse `dragenter`, `dragover` and `drop`, and made the macOS view register no dragged type. Windows had no native counterpart, because WebView2's switch (`ICoreWebView2Controller4::put_AllowExternalDrop`) sits behind a controller choc keeps private, and choc declares only Controller and Controller2. This adds that layer. It is defence in depth: the page guard and the navigation rule (ADR-196) already apply on Windows, and each stands without this one.
- **What changed:**
  - `libs/patches/choc-webview2-external-drop.patch` (new), against the pin `a08bfd8`. Three hunks, 52 added lines, none removed:
    1. `Options`: `bool allowExternalDrop = true;` with its doc comment, after `acceptsFirstMouseClick`.
    2. After `ICoreWebView2Controller2`: `enum COREWEBVIEW2_BOUNDS_MODE {};`, `ICoreWebView2Controller3` (eight methods) and `ICoreWebView2Controller4` (two methods and `getIID()`).
    3. In `webviewControllerCreationComplete`, after the `transparentBackground` block: when the option is false, `QueryInterface` for Controller4, and if it returns `S_OK` with a non-null pointer, `put_AllowExternalDrop (FALSE)`.
  - **Name.** The brief asked for `<next number>-…external-drop….patch`. The existing two are not numbered: the convention in `libs/patches/README.md` is `<submodule>-<what>.patch`, and `choc_patch_check` finds patches by `choc-*.patch`. I followed the convention.
  - **One deliberate difference from the brief's wording.** The brief described the call as `put_AllowExternalDrop(options.allowExternalDrop ? TRUE : FALSE)`. The patch makes the call only when the option is false, and passes `FALSE`. With the option at its default nothing is queried and nothing is called, so "default unchanged" holds by construction, as it does for the other two patches and for choc's own `transparentBackground` block just above. For horde, which passes false, the two forms make the same call. Raised to the lead as an open question below.
  - `CMakeLists.txt`: the patch is third in `HS_CHOC_PATCHES`.
  - `src/gui/hypersaw_gui_common.h`: `makeWebView` takes `bool allowExternalDrop = true` between `allowPermission` and `customSchemeURI`, and assigns it. The origin stays the last parameter, so the existing origin rule and its control C19 are untouched. macOS passes nothing and keeps choc's default.
  - `src/gui/hypersaw_gui_win.cpp`: passes `false`, with a header paragraph on the three layers.
  - `tools/choc_patch_check.py`: covers the third patch. New row DROP, read from the patch's own added lines so it runs with no choc checkout (CI's fast job). APPLY adds the chain and position rules. ORDER now runs every ordering of the list (six for three patches), not only the reverse. UPSTREAM watches two more names. WIRING has three more rules. Controls go from 23 to 38.
  - `libs/patches/README.md`: the new row; "either" became "any one".
  - `verify`: the comment on the existing `choc_patch_check` line describes the third patch and says thirty-eight controls. No check was added, removed or relaxed there.
  - Private, not tracked: `local/security/choc-upstream-draft-external-drop.md`, a feature-request draft. Not posted.
- **The interface ids and where they come from.** `build/native/include/WebView2.h` in the NuGet package Microsoft.Web.WebView2, version 1.0.2903.40, downloaded from nuget.org to a scratch directory and not committed (SHA-256 of the header: `8d298691104964129bd6bd8fc3119608607d794135752dc02217f72f7bddedb1`).
  - `ICoreWebView2Controller3`: `f9614724-5d2b-41dc-aef7-73d62b51543b`, derives from Controller2.
  - `ICoreWebView2Controller4`: `97d418d5-a426-4e49-a151-e1a10f327d9e`, derives from Controller3.
  - The package's own XML documentation says of `AllowExternalDrop`: "The default value is true."
  - `tools/choc_patch_check.py` holds the four-interface chain as `SDK_CHAIN`. A scratch script parsed the SDK header and asserted that the record equals it (ids, bases, method names in order).
- **The new controls (C24 to C38), each must read red:**
  - WIRING: the backend without its argument (C24); the backend passing true (C25); `makeWebView` without the assignment (C26).
  - LIST: a list missing the patch (C27). SHAPE: the patch with a removed upstream line (C28).
  - DROP: the option defaulting to false (C29); a call made whatever the option says (C30); two Controller3 methods swapped (C31); an interface id one digit off (C32); a `getIID()` that disagrees with its `MIDL_INTERFACE` line (C33); a call made when the query did not succeed (C34).
  - Chain: an upstream controller interface with a method missing (C35).
  - Apply: a choc whose controller set-up drifted stops the patch applied alone (C36); a planted patch that leans on the navigation patch's lines does not apply alone (C37) and fails ORDER (C38). The plant applies in list order, so it is a real patch.
  - I printed which error each planted fault raises, once, by hand. Each was red for its own rule and not for a neighbour's.
  - One existing control caught a mistake of mine. A comment after the new argument's comma hid the origin argument from C19's text edit, and C19 read green. I moved the comment above the argument; C19 was not changed.
- **Composition (Layer-0, deterministic, the build's own `apply_patch.cmake`):** the three patches apply in list order; all five other orderings give the same bytes; each applies alone to the pristine header; a CRLF copy of the header patches to the same bytes; `libs/choc` stays clean.
- **Compiled or run on this Mac:**
  - A real configure (`cmake -G "Unix Makefiles"`) applied the three patches, and the `HYPERSAW-impl` target built with no warnings. That compiles the patched `Options`, `makeWebView` and `hypersaw_gui.mm`. It does not compile the header's Windows section.
  - A scratch probe, compiled and run on the host. It takes three verbatim slices of the patched header (the four controller declarations, `COMPtr`, the new block) and the SDK header's four declarations, verbatim. A fake controller implements the chain as the SDK declares it, and the patched block is run against it through choc's declarations, as it would be on Windows. Results: option false with Controller4 available, the calls are `QueryInterface` (success), `put_AllowExternalDrop(FALSE)`, `Release`; option true, nothing is called; option false on a runtime without Controller4, one failed `QueryInterface` and nothing else. Control: with one Controller3 method dropped from choc's declarations, the same call reaches `get_AllowExternalDrop` instead, so the probe can see a wrong slot.
  - The same slices, with no includes and with the real macro expansions (`__declspec(uuid)`, `__declspec(novtable)`, `__stdcall`), pass `clang++ -fsyntax-only -fms-extensions` for the x86_64, i686 and aarch64 `*-pc-windows-msvc` targets. `static_assert`s on `__uuidof` confirm the two ids as the compiler reads them (a wrong value fails, checked). clang's MS-ABI vtable dump for x86_64 puts `get_AllowExternalDrop` at slot 36 and `put_AllowExternalDrop` at slot 37, the slots the SDK header's declaration order gives.
- **Not compiled or run here:**
  - The patched header's Windows section as a whole, and `src/gui/hypersaw_gui_win.cpp`. This Mac has no Windows SDK and no MSVC standard library, so nothing that includes `<windows.h>` compiles. The syntax check above used hand-written stand-ins for the Windows types, not Microsoft's headers, so it shows the slices are well-formed and consistent with each other, not that they agree with the real `BOOL`, `HRESULT` or `IID`. The PR's CI jobs `build-windows` and `validate-windows` are the compile proof.
  - Any run-time behaviour on Windows. That `put_AllowExternalDrop(FALSE)` makes WebView2 refuse a real drop from another application comes from Microsoft's documentation, not from a run. The run-time proof is the human's Windows test pass (B447).
  - Guaranteed versus measured: the composition rows and the 38 controls are Layer-0 and CI-blocking. The probe and the MSVC-target checks are one-off scratch evidence, not wired, because they need the SDK header, which this repository does not carry.
- **Evidence consulted:** the brief; ADR-196 and its Amendment 1; ADR-205 (`origin/lead-records-230`); ROADMAP B448; `libs/patches/README.md`, both existing patches, `apply_patch.cmake`; `tools/choc_patch_check.py`, `tools/embedded_page_policy_check.py`; `src/gui/hypersaw_gui_win.cpp`, `hypersaw_gui_common.h`, `embedded_page_policy.h`, `hypersaw_gui.mm`; `libs/choc/choc/gui/choc_WebView.h` at the pin (`Options`, the COM declarations, `webviewControllerCreationComplete`); the SDK's `WebView2.h`; `traces/2026-10-08-b446-choc-win-clipboard.md`, `traces/2026-10-09-b448-c3-gui-drop-guard.md`.
- **Alternatives rejected:**
  - Calling `put_AllowExternalDrop` on every creation with the option's value: see the deliberate difference above.
  - Declaring only Controller4, or Controller4 directly on Controller2. Its two methods would land eight slots early and call `get_RasterizationScale` and `put_RasterizationScale`.
  - Adding the new `makeWebView` parameter last. It would have meant editing the existing origin rule and control C19.
  - A named constant for the backend's `false`. A comment says it, and the check pins the position.
  - Wiring the slot probe as a check. It needs the SDK header; vendoring it would add a dependency.
- **Verify:** `./verify fast`, exit 0, on this change set. The hash and the JSON of the run on the committed tree are in the PR body, since a trace cannot hold its own commit's hash. `./verify full` was not run; the brief's target is `fast`.

# parity-scenario-floors — eight golden-parity gates fail below a pinned scenario count

- **Queue item:** ROADMAP B455, finding H1 of `docs/audits/2026-10-10-repo-audit.md`; DECISIONS ADR-206 item 1 (on PR #1028 when this was written), which the human approved. Lead brief of 2026-10-10 (horde lead session). The brief carried its own goal list and did not quote ROADMAP text verbatim; the B455 row agrees with it ("the fix is a floor per gate at today's count").
- **Why:** `parity_check` (L0-1) and seven siblings loop over a manifest the golden generator writes and go red only when a failure was counted. An empty manifest, or a deleted scenario block, counts none and reads GREEN. Each gate now fails below its pinned scenario count, and a must-fail check proves it.
- **H1 reproduced** before any edit, each gate against a directory holding only a zero-byte manifest (Release build of this branch's base): all eight exit 0. Last lines: `parity_check: 0/0 scenarios within eps=1e-06 (worst 0.000e+00 @ )`, and `<gate>: GREEN (0 failures; worst parity rms 0)` for the other seven.
- **What changed:**
  - `tools/scenario_floor.h` (new, 36 lines): `scenarioFloorHolds(gate, count, floor)`. Below the floor it prints `FAIL <gate>: N scenarios, below the pinned floor of F ...` and returns false; above it prints `NOTE ... raise the floor in the same PR` and returns true; equal prints `OK`.
  - Seven gates (`filter`, `notch`, `spectra`, `swarmalator`, `time`, `station`, `subosc` `_check.cpp`) include it, count their manifest scenarios and add one `kMinScenarios` and one failure increment before the summary line. Counts and floors, read off the real corpus: filter 11, notch 11, spectra 9, swarmalator 9, time 11, station 32, subosc 54. Station and subosc skip `#` lines and count `scenarios.size()`; the other five count non-empty lines, before the missing-golden `continue`. A missing manifest already failed in all seven (return 1) and still does.
  - `parity_check`: floor 156, held in `tools/parity_floor_check.py` (PARITY_FLOOR), NOT in `tools/parity_check.cpp`. That file is the pinned source of horde 2's lift: `h2/cores/swarm/lift-ledger.json` holds its git blob and `tools/h2_swarm_parity_check.cpp` is rebuilt from it byte for byte (`tools/h2_lift_check.py`, FROZEN set). Editing it turns `h2_lift_check` red and needs an h2/ re-lift, which the brief forbids touching. Deviation from the brief's "in the gate's own source", for that reason only.
  - `tools/parity_floor_check.py` (new, `WIRED: ./verify full`) and one invocation in `verify` (full, after `time_check`, comment "Added under ADR-180 §1"). For each of the eight gates, against symlinked scratch copies of the real corpus: POSITIVE (unmodified reads green), EMPTY (empty manifest reads red), DROP (last scenario removed reads red). A red control must carry the floor's own words, so a gate that fell over for another reason cannot pass as a control. 24 control rows, ~20 s.
  - README.md and docs/ROBUSTNESS.md say "156/156"; the count is still 156, so they are unchanged.
- **Evidence consulted:** `docs/audits/2026-10-10-repo-audit.md` H1 and L7; the eight gate sources; `tools/h2_lift_check.py` and `h2/cores/swarm/lift-ledger.json` (why parity_check.cpp is untouched); `tools/test_table_check.py` (wiring grammar: line-anchored marker, invocation parsed from `verify`); `tools/tolerance_registry_check.py` (integer thresholds are not inventoried, so `kMinScenarios` and `PARITY_FLOOR` register nothing; the names avoid its tolerance words); `verify` h2_engine_parity_check TRUNC block (the control style).
- **Alternatives rejected:** one shared rig for the five near-identical gates (L7), because it restructures the gates and the brief says not to; a floor inside parity_check.cpp plus a re-lift of the h2 copy and its ledger, because h2/ is out of scope; a failing (not noting) result when the count rises, because the brief lets a count rise freely.

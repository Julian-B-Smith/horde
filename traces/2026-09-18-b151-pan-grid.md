# b151-pan-grid — pan motion onto the gravity grid: BLOCKED, the paired reference edit is out of scope

- **Queue item:** B151 (ratified 2026-09-18, option (a): pan motion moves onto
  the gravity grid; re-baseline under B81; then remove `subdiv_check`'s
  pan-motion exclusion).
- **Outcome:** grounded refusal. **No source file changed.** The DSP change was
  built and measured, then reverted; this entry is the measurement.

## Why it is blocked

B151(a) cannot be executed inside the dispatched file scope
(`src/swarm_core.h`, `tools/subdiv_check.cpp`, `tools/blocksize_check.cpp`,
goldens-via-generator). The C++ edit alone is correct and achieves the
invariant, but it puts the core 600x over the L0-1 parity bar, and the only
lever that can move the goldens back is `reference/swarmsaw.html` — explicitly
out of scope in the brief and a protected path in CLAUDE.md ("they ARE the
reference — an edit there is a spec change").

**The goldens are not a re-baselineable artifact.** `build-golden/` is
gitignored (`.gitignore:9-12`, "goldens are generated artifacts, only the
generator is committed"); `./verify full` regenerates all 156 from
`reference/swarmsaw.html` on every run (`verify:191-193`). There is no
committed golden byte to move. A golden moves if and only if the reference
moves. `tools/golden/extract_core.mjs` evals the core straight out of the HTML
and has no divergence or expected-exception mechanism; `parity_check` is a flat
eps=1e-6 RMS test with no exception list.

**ADR-086 is the precedent, and it was a PAIRED edit.** The DYN reference
carries the gravity grid itself (`reference/swarmdynamics.html:420-425` —
`room`/`gravAccum`/`gravityStep(grid/sr)`), matching `src/swarm_core.h:812-832`.
Gravity moved onto the grid on both sides at once. `reference/swarmsaw.html`
has no grid at all (grep for `gravAccum`/`gravityStep`/`GridSeconds`: zero
hits) and computes pan motion per render call at
`reference/swarmsaw.html:596` — `const dtB = outL.length / sr`. B151(a) is the
same class of change as ADR-086 and needs the same paired edit plus an ADR, per
the domain invariant "any intentional divergence from the prototypes requires
an ADR".

## What was measured (all figures verified, not entailed)

Experiment applied to `src/swarm_core.h` `render()`: advance pan motion at the
START of each gravity-grid period instead of once per call —

```cpp
    int done = 0;
    while (done < frames)
    {
      const int grid = gravGridSamples();
      if (gravAccum == 0) advancePanMotion(grid);   // was: advancePanMotion(frames) pre-loop
```

Five lines, no new clock: it reuses the ADR-086 `gravAccum` accumulator, and
the rates (`0.1`, `0.08 + i*0.021`) were already per-SECOND, so ADR-009 needed
nothing — only the zero-order-hold cadence moves.

**The invariant is achieved.** `subdiv_check` all four rows `0` exactly
(including pan motion and "both", today's KNOWN exclusions).
`blocksize_check` all eight rows `0` exactly across {1, 7, 64, 256, 333, 1024}
x {44.1, 48} kHz, pan-motion rows included.

**The parity cost.** 147/156, worst 6.119e-04 — exactly the nine pan-motion
scenarios move, nothing else:

| golden | RMS delta | character |
|---|---|---|
| `pan-drift.seed1234/777/42` | 2.402e-04 | per-voice pan LFOs sampled every 256 samples instead of every 1024; the drift is the same trajectory, resampled 4x finer |
| `pan-sweep.seed1234/777/42` | 1.515e-04 | the single shared sweep, same |
| `centre-pin.seed1234/777/42` | 6.119e-04 | largest — the centre pin scales the offset by focus distance, so the finer cadence compounds with `driftMode 1` |

RMS is seed-invariant to 4 s.f. within each scenario, which is itself evidence
the difference is the cadence and not the seeded stream.

**The reference block size is 256 frames at 44.1 kHz, and this is measured, not
chosen by argument.** Driving the UNMODIFIED reference in 256-frame sub-blocks
inside the parity protocol's 1024-frame note-off cadence reproduces the grid
build **bit-identically — rms = 0.000e+00 on all nine**
(`scratchpad/b151/subblock.mjs`, manifest rows reused verbatim from
`build-golden/manifest.tsv`). So the C++ grid form IS "the reference at a
256-frame block", exactly, and the paired reference edit has a defined target.

Confounder found and removed en route: regenerating the whole corpus at
`BLOCK = 256` gives 0/156, not 9 failures, because `renderScenario` fires
note-off at the first block boundary >= 3 s — 133120 at 1024 vs 132352 at 256.
That run measures note-off timing, not pan cadence. The sub-block harness keeps
note-off on the 1024 grid, which is why its zeros mean something.

## Alternatives rejected

- **Make the pan grid 1024 samples so parity passes unchanged.** Rejected as
  gate-defeat. Parity always renders at 1024, so this buys green by making both
  sides share the subdivision — precisely the blindness
  `tools/subdiv_check.cpp`'s header names ("BOTH SIDES USE THE SAME
  SUBDIVISION and parity agrees with itself") and L0031 warns about. It would
  also still disagree with the per-call reference at every other host block.
- **Edit `reference/swarmsaw.html` here.** Out of scope, protected path, and
  needs an ADR — the lead's call, not mine.
- **Land the C++ change red and flag it.** Rejected: charter ("a red oracle
  halts forward work"), and a red branch that can be merged by a badge is the
  L0004 hazard.

## What the lead needs to decide

B151(a) needs a re-brief with `reference/swarmsaw.html` in scope and an ADR

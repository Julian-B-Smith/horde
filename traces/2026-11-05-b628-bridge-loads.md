# b628-bridge-loads — the bridge answers GUI 3's hello and preset as loads, in a 980 × 720 window

- **Queue item:** B628, the GUI session's three bridge changes for its plug-in mode, relayed by the lead (follows `traces/2026-11-05-b628-bridge.md`).
- **Why:** in plug-in mode the page adopts a frame carrying every engine row, once its ack reaches a pending `hello` or `preset`, as a LOAD: it takes the values, sends nothing back, and starts its undo fresh. The bridge must therefore send the full set only in the frame that completes a load. For a preset that frame must come after the audio thread's swap, or the page would adopt the old preset's values. While a load is pending, frames hold `ack` below its seq and carry no `params` or `presets`. A preset completes when the live slot's generation and preset, which the audio thread publishes at the swap as one word, show an engine built for that preset after the message came. Loading the preset already playing forces a rebuild, so its own values replace edits. Once a page has said hello, the window's resend-until-delivered path is off, so a full set never goes out unasked. The window is fixed at 980 × 720, where the page places its device.
- **Evidence consulted:** the GUI session's staged `docs/design/gui3/device.js` (loadAt, adopt, everyRow) and `engine-stub.js` (hello in the schema, Merger keeping hello, mismatch, refused) in its worktree, read only; the page built from a scratch copy of that working tree (its changes are staged, not committed on `gui-plugin-mode`; inlined page sha256 c8b1d073…).
- **Alternatives rejected:** acknowledging a preset when its message is applied (the old path: the page would adopt the old engine's values; this is now the smoke test's control); sending on-change rows and presets during a pending load (the page would take the new preset's values as engine-originated before the load frame); re-recording the replay fixture (it reproduces unchanged, byte for byte).

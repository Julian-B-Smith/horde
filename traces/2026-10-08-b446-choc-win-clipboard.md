# b446-choc-win-clipboard — the Windows web view does not grant clipboard reads to page script; choc is marked patched in the SBOM

- **Queue item:** ROADMAP B446 (security overhaul), ADR-196. Lead brief of 2026-10-08 (horde lead session). The human approved extending the carried choc patch on the lead's recommendation ("I don't totally understand what choc is so I can't rule on it with confidence but will follow your recommendation"). That approval covers only this change. The brief carried the acceptance criteria; the ROADMAP row does not yet hold this item's acceptance text.
- **Why:** W3a (#965) turned clipboard reads off for page script on macOS and routed PASTE through a native binding, `hzPasteState`. On Windows, choc's WebView2 `PermissionRequested` handler grants every clipboard read a page asks for (`libs/choc/choc/gui/choc_WebView.h:1739-1740` at the pin), and an app cannot change that from outside choc. The navigation trace (`traces/2026-10-08-b446-choc-win-nav.md`) also left the SBOM showing choc at its upstream commit with no mark that the build patches it.
- **What changed:**
  - `libs/patches/choc-webview2-permissions.patch` (new). It adds `WebView::Options::PermissionKind {clipboardRead, microphone, camera, geolocation, notifications, otherSensors, other}` and `std::function<bool(PermissionKind)> allowPermission`. When the option is set, the WebView2 `PermissionRequested` handler maps the kind (an unknown kind maps to `other`), asks the option, sets `STATE_ALLOW` or `STATE_DENY`, and returns before upstream's grant. With the option unset, the handler runs exactly as upstream. The patch only adds lines: 45 added, 0 removed, per `git apply --numstat`.
  - **Mechanism: a second patch file, applied in order.** I chose this over extending the navigation patch for three reasons. First, the two halves have separate upstream fates: navigation is Tracktion/choc#111, and permissions would be a follow-up. Second, a separate file can be dropped by itself. Third, the SBOM can list each patch with its own hash. Both patches are made against the pristine pin, and neither changes a line the other's hunks rely on. Each therefore applies alone and in either order, with the same result in both orders. I checked this by hand, and the check's ALONE rows check it on every run.
  - `libs/patches/apply_patch.cmake`: `PATCH` is now a CMake list, and each patch is checked and applied, in order, to the copy the previous one left. The drift stop, the "exited 0 but unchanged" stop, and the missing-file stop are kept for each patch. Applying the same patch twice fails loudly, which I checked by hand.
  - **Pre-existing CRLF bug, fixed in the same file.** The CRLF normalisation never ran. CMake's `file(READ)` drops the CR of each CRLF pair (measured on CMake 4.1.2: `a\r\nb\r\n` reads as length 4), so the script's `string(FIND "\r\n")` test never fired, and a CRLF header was left untouched. The `origin/main` script, run on a CRLF copy of the header with the navigation patch alone, stops with `NO LONGER APPLIES`. The fixed script normalises and rewrites every target unconditionally. A CRLF copy now patches to bytes identical to the LF copy, and an LF file round-trips unchanged: the patches-only-permissions output is byte-identical to the authored copy. This contradicts the navigation trace's "A CRLF copy of the header patches to the same bytes as the LF one". That trace is not edited (traces are append-only); this entry is the correction.
  - `CMakeLists.txt`: `HS_CHOC_PATCHES` replaces `HS_CHOC_PATCH`. It lists both patches in order and is passed quoted (`"-DPATCH=${HS_CHOC_PATCHES}"`), because unquoted, the `;` would split the list into separate arguments. It is also the source the SBOM reads.
  - `src/gui/embedded_page_policy.h`: `webPermissionPolicy(kind)` returns false for every kind. It is templated on the kind enum, like `embeddedPagePolicy`. The page uses no microphone, camera, location, notification or sensor API; I grepped `src/gui/gui*.html` for `getUserMedia`, `geolocation`, `Notification`, `requestMIDIAccess` and file pickers and found nothing.
  - `src/gui/hypersaw_gui_common.h`: `makeWebView` takes an optional `allowPermission` and assigns it.
  - `src/gui/hypersaw_gui_win.cpp`: it passes `detail::webPermissionPolicy` and binds `hzPasteState`. The binding uses `OpenClipboard`, `CF_UNICODETEXT` and `GlobalLock`, scans with `wcsnlen` bounded by `GlobalSize`, and converts with `WideCharToMultiByte(CP_UTF8)`. The text goes to `host.applyStateJson`, and only a status comes back (1 applied, 0 nothing to paste, 2 not a patch), as on macOS. The page (`src/gui/gui2.html`) already prefers `window.hzPasteState` when it exists. Only its comment changed, to say that this now covers Windows.
  - `tools/embedded_page_policy_check.cpp`: 7 permission rows (every kind refused) and two must-fail controls. The first is upstream choc's rule (clipboard reads granted); the second is a deny-list of the known kinds only (a new kind granted). Each is caught by 1 row.
  - `tools/choc_patch_check.py`: now covers both patches. New rows are LIST (`HS_CHOC_PATCHES` equals the `libs/patches/choc-*.patch` files, and the README names each), PIN and SHAPE for each patch, APPLY with navigation and permission content rules, ALONE for each patch, CRLF, UPSTREAM for both names, and WIRING (both options assigned, both policies passed, `hzPasteState` bound, the list quoted). It has 16 must-fail controls; C10 to C16 are new. The list is read through `gen_sbom.carried_patches`, the same reader the SBOM uses. I showed the CRLF row is red when the check is pointed at the `origin/main` script.
  - `tools/gen_sbom.py`: choc's component carries CycloneDX 1.5 `pedigree.patches`, one `{"type": "unofficial", "diff": {"text": <patch text>, "url": "libs/patches/<file>"}}` per patch in apply order, plus `pedigree.notes`. It also carries a `horde:patch` property `<path> sha256:<hex>` for each patch, because CycloneDX 1.5 has no hash field on a patch. It fails closed on a listed patch that is missing, a list naming no submodule, or a `libs/patches/*.patch` that no list names.
  - `tools/release_path_check.py`, rule 5 (pure, read from the tree, not from the generator): every `libs/patches/<submodule>-*.patch` must appear in that component's pedigree, with matching text and a matching SHA-256 property. Four controls run on this tree's SBOM: the pedigree removed, one patch dropped, a wrong hash, and altered text. By hand, a generator with the pedigree stripped read red with 4 findings.
  - `libs/patches/README.md`: describes the list, the order, the SBOM marking, the naming convention and the new row. The navigation row and the navigation patch's `UPSTREAM STATUS` header now cite #111. That is a header-only text change; its diff body is unchanged.
  - `verify`: the comments on the two existing choc lines are updated to describe the strengthened checks. No check was added or removed there. Both checks were already wired.
  - Private, not tracked: an "Addendum for issue #111" section was appended to `local/security/choc-upstream-draft.md` in the main checkout. It is a factual follow-up comment draft with the patch body. Not posted.
- **Verified (Layer-0, deterministic, on this Mac):**
  - Both patches apply, in either order and each alone, through the build's own script.
  - A CRLF copy of the header gives the same bytes as the LF copy.
  - `libs/choc` stays clean.
  - The permission rule refuses every kind (by test).
  - The Windows wiring holds (by source-level check).
  - The SBOM pedigree carries each patch with its SHA-256 (it matches `shasum -a 256`).
  - The macOS plugin and `gui_webview_check` compile against the twice-patched header in `./verify full`.
- **Not verified:**
  - Runtime behaviour on Windows. No WebView2 runtime exists on this Mac, and the patched Windows branch and `hypersaw_gui_win.cpp` are compiled only by CI's Windows jobs. Three things come from Microsoft's documentation, not from a run: that `STATE_DENY` makes `navigator.clipboard.readText()` reject; that a typed Ctrl+V into a text field still works (it is a user paste, not a permission request); and that native PASTE applies a patch. B447 gates these behind a human check in a Windows host.
  - The SBOM was not run through a CycloneDX schema validator. None is installed, and adding one is a dependency. The field names follow the 1.5 specification as I understand it.

- **Alternatives rejected:**
  - Extending the navigation patch: see Mechanism.
  - A `bool allowClipboardRead` option. It is smaller, but it cannot refuse the other kinds, and it would still leave the decision split between choc and the app.
  - Denying only clipboard reads and leaving other kinds at WebView2's default. The default can show a prompt the user might accept, and the GUI needs none of those kinds.
  - Sharing one paste helper between the macOS and Windows backends. That would mean touching `hypersaw_gui.mm`, which is not needed here.
  - Embedding the SHA-256 in `pedigree.notes`. It is not machine-readable; a property is.
  - A `diff.url` pointing to GitHub. It would need the remote and the commit, and it would not be deterministic across clones.

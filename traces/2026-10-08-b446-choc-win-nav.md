# b446-choc-win-nav — the Windows web view admits only its embedded page, through a documented choc patch applied at configure time

- **Queue item:** ROADMAP B446 (security overhaul), ADR-194 D-S5. Lead brief of 2026-10-08 (horde lead session). The human approved it in their own words: "Approve the choc patch". That approval is the gate for patching vendored code, and it covers only this change. The brief carried the acceptance criteria; the ROADMAP row records the Windows gap ("The Windows navigation hooks need a `libs/choc` change (the D-S5 decision, with the human)") but not this item's acceptance text.
- **Why:** W3a (#965) applied the rule on macOS: the view shows only the embedded page, and only that page reaches the bridge. That trace recorded that Windows could not follow. choc keeps `ICoreWebView2` private, and `getViewHandle` returns only the HWND, so the wrapper could not reach `NavigationStarting`, `FrameNavigationStarting`, `NewWindowRequested` or a message's source.
- **What changed:**
  - `libs/patches/choc-webview2-navigation.patch` (new). It adds `WebView::Options::NavigationType {page, frame, newWindow, message}` and `std::function<bool(NavigationType, const std::string& uri)> allowNavigation`. The WebView2 backend consults the option from the three navigation events (two handler objects, because page and frame share one handler interface) and from `WebMessageReceived` (its `get_Source`). The patch declares the four WebView2 interfaces it needs, with IIDs and method order checked against the published `WebView2.h` (NuGet Microsoft.Web.WebView2 1.0.2903.40, downloaded to scratch for this comparison only; nothing from it is vendored). The patch only adds lines (149 added, 0 removed, per `git apply --numstat`; the first version of this trace said 123, a count that skipped blank added lines). With the option unset, no new handler is registered and the message path runs exactly as upstream. The header states the purpose, base commit, upstream status and removal condition.
  - `libs/patches/apply_patch.cmake` (new). It copies `libs/choc/choc` to `<build>/choc-patched/`, normalises the patched files to LF, and runs `git apply --check`, then `git apply`. It stops with a `FATAL_ERROR` if the patch does not apply. It also stops if `git apply` exits 0 but a target is unchanged. `libs/patches/README.md` (new) describes the mechanism, the patch's row and the bump procedure.
  - `CMakeLists.txt`: runs the script at configure time, with `CMAKE_CONFIGURE_DEPENDS` on the patch, the script and the upstream header. It puts `HS_CHOC_DIR` on the impl's PUBLIC include path.
  - `src/gui/hypersaw_gui_common.h`: includes `<choc/gui/choc_WebView.h>` (the patched copy). `makeWebView` takes an optional `allowNavigation` and assigns it to the options. macOS passes none.
  - `src/gui/hypersaw_gui_win.cpp` passes `detail::embeddedPagePolicy` (`src/gui/embedded_page_policy.h`, after the critic round below). The policy admits exactly one page load, at `kEmbeddedPage` (`https://choc.localhost/getHTMLInternal`, where choc's `setHTML` serves the page on Windows). It refuses every frame navigation and every new-window request, and delivers a message only from the admitted page, with the message source's `#fragment` ignored.
  - `tools/gui_webview_check.mm`: includes the patched header through the include path. Otherwise it would hold a second, different definition of `WebView::Options` beside the impl it links.
  - `tools/choc_patch_check.py` (new, `WIRED: ./verify fast`, ADR-180 §1). Rows: PIN, SHAPE, APPLY (it runs the build's own script), UPSTREAM and WIRING. It has ten must-fail controls. It prints a WARNING instead of the APPLY rows where `libs/choc` is not checked out, as in CI's verify-fast job.
- **Mechanism chosen:** option (a), a patch file applied at configure time to a build-tree copy. A drifted upstream context fails the configure (measured: control C1, and a hand test that changed one context line and got `NO LONGER APPLIES`). PIN fails on any bump, even one the patch still applies to, so the removal condition is re-asked every time. A relative include of the unpatched header fails WIRING. Building with the unpatched header cannot happen quietly either: `opts.allowNavigation` would not compile.
- **Verified (Layer-0, deterministic):**
  - The patch applies to the pinned choc `a08bfd8`, through the build's own script.
  - The patched file is byte-identical to the authored copy.
  - A CRLF copy of the header patches to the same bytes as the LF one, which covers the Windows `core.autocrlf` checkout.
  - `libs/choc` stays clean in `git status`.
  - The macOS plugin and `gui_webview_check` compile against the patched copy. Their `.o.d` dependency files name `choc-patched/choc/gui/choc_WebView.h`, and no target names the unpatched header.
  - The policy's behaviour, by test (`embedded_page_policy_check`, after the critic round). Its wiring, by source-level check: the Windows backend passes the shared policy, and `kEmbeddedPage` matches choc's `getURIHome` + `getHTMLInternal`.
  - The draft's UTF-8 reproduction prints `read past terminator` when built with `-O2 -DNDEBUG` against the pinned choc.
- **Not verified:** runtime behaviour on Windows. No WebView2 runtime exists on this Mac, and the patch's Windows branch is compiled only by CI's `build-windows` (see Verify). That WebView2 really cancels a refused navigation, suppresses a handled popup, and reports the page URI exactly as `https://choc.localhost/getHTMLInternal` in `NavigationStarting` and `get_Source` comes from Microsoft's documentation and the SDK header, not from a run. A human check is needed in a Windows host: the GUI loads, the bridge works, and the plugin behaves as before.
- **Evidence consulted:** the brief; ADR-194; the W3a trace and `src/gui/hypersaw_gui.mm` (`navGuardClass`, `lockToEmbeddedPage`); the private P0 lane-2 report, W2-02; `libs/choc/choc/gui/choc_WebView.h` (Options, WebView2 declarations, `Pimpl`, `EventHandler`, `getURIHome`, `setHTML`); `libs/choc/CONTRIBUTING.md` (issues, not pull requests); `WebView2.h` from the SDK package (IIDs, vtable order, `add_FrameNavigationStarting`'s handler type); the W1a trace, PR #952 and `tools/bridge_utf8_check.cpp` (the UTF-8 control); `.github/workflows/ci.yml` (verify-fast checks out no submodules; the Windows build does); `.gitattributes` (LF in the superproject; choc has none of its own); `tools/test_table_check.py`.
- **Alternatives rejected:**
  - A uri-only callback, as the brief's example suggests. It cannot tell a page load from a frame load or a message source, and the policy needs all three.
  - Adding the new interfaces to choc's `EventHandler`. That changes an upstream line; a separate `NavigationFilter` keeps the patch purely additive.
  - Patching the submodule's working tree at configure time. That makes `libs/choc` dirty and the build id `+`.
  - Vendoring a full patched copy of `choc_WebView.h`. A bump would not fail on it, and its diff cannot be reviewed.
  - `git apply --ignore-whitespace` for CRLF checkouts. I could not test it here; LF normalisation is deterministic and was tested.
  - A configure-time hash pin of the upstream file. PIN already covers bumps, and a hash would need its own CRLF handling.
- **Critic round (lead's follow-up, 2026-10-08; verdict APPROVE WITH CHANGES).** This trace is amended in place, not superseded, because the PR was unmerged and the lead asked for the corrections here.
  - MEDIUM-1: the policy moved into a pure, standard-library-only header, `src/gui/embedded_page_policy.h`. It is a template on the kind enum, so its check needs no choc checkout. `hypersaw_gui_common.h` includes it.
    - The header is separate rather than inside `hypersaw_gui_common.h`, because that file includes generated headers that `./verify fast` cannot build.
    - New: `tools/embedded_page_policy_check.cpp`, plus `tools/embedded_page_policy_check.py`, which compiles it with the host compiler; wired into `./verify fast`.
    - It runs 23 rows in three fresh-state sequences: the first page is admitted and a second refused; a wrong or prefixed URI first is refused with no latch spent; a message before admission, from another URI, from a prefixed URI, with a query or with no source is refused; a `#fragment` is tolerated; frames and new windows are refused.
    - It has four must-fail controls: accept-any-source (4 rows catch it), a dropped latch (3), prefix matching (5) and exact-match messages (1).
    - `choc_patch_check` WIRING no longer token-matches the policy body. Its old C7 and C8 are gone; the new C7 is "the backend passes another rule".
  - MEDIUM-2: the message source is compared with its `#fragment` removed. `gui_sink_check` gains a URL-change rule: no `pushState`, `replaceState`, `location.hash` or `href="#` in `src/gui/gui*.html`. It has 9 planted cases (6 flagged, 3 not), and a planted `href="#top"` in a copy of `gui.html` was red end to end.
  - LOW-1: `CONFIGURE_DEPENDS` now covers every file in `libs/choc/choc` and the submodule's HEAD file.
  - LOW-2: the count is corrected to 149 (above).
  - LOW-3: the runtime-unverified caveat is in `hypersaw_gui_win.cpp` and in the README row.
  - LOW-4: the README states that configuring requires git.
  - LOW-5: the upstream draft says the option is WebView2-only, so it must be implemented elsewhere or documented as such.

# b89-intent-pad — B89 phase 2d: the MAIN pad becomes the performance pad (§4.4 spring, latch, corner-owned home)

- **Queue item:** ROADMAP B89 (phase 2 paragraph), increment 2d of
  `docs/proposals/b89-phase2-intent-resolver.md`; ADR-176 §5 + A3, ADR-152
  (SPEC-INTENT-BUS §4.4/§5/§7), ADR-150 (the MAIN pad's own assignment pair).
  Builds on 2a (PR #629), 2b (PR #654) and 2c (PR #660, branch
  `b89-intent-apply`).

- **Why:** 2c made the resolver's value reach the engine but read the ten
  intents as raw INPUTS — X and Y were just the two macros ADR-150's
  assignment names. 2d makes them what §4.4 says they are: the puck's
  DISPLACEMENT from the home of whichever corner owns the `home` atom. Two
  decisions shaped the diff.
  1. **The shell writes neither pad parameter.** The puck is separate state
     and the two macro ids are its POINTER, so a spring return can never
     fight a host (or a hand) for the parameter it is reading, and turning the
     flag on cannot move a value the player is holding. The alternative — make
     the pad params BE the puck — would have put a 172 Hz writer on two
     host-automatable ids.
  2. **Drag is a BRACKET, not a value.** A released pointer leaves the
     parameter exactly where it was, so no reading of the two macro values can
     distinguish "still held" from "let go"; only the gesture bracket can.
     The latch is therefore fed from `drainQueue`, which is where gesture
     messages already cross to the audio thread IN ORDER with the values they
     bracket — a second path would have been a second clock. This is also why
     `hostIf.gesture`'s two lines became `Plugin::guiGesture`: the oracle opens
     the same bracket through `hypersaw_debug_gesture` rather than a
     test-only shortcut, so what T8 exercises is the shipped path.

- **Alternatives rejected:**
  - *Generating a 33rd golden for the pad.* Not needed, and a redundant
    fixture is a maintenance cost with no evidence in it: 2a already ships
    `t8-release-return`, `t8-latch-hold`, `t8-retarget` and `t8-drag-stiff`,
    each holding `padStep` to the prototype's own trajectory at 1e-6 with its
    must-fail control firing (`intent_check` prints all four). What the
    instrument needed was the half the header cannot see, which is T8a–e.
  - *A `hypersaw_debug_drag` door.* Rejected: it would have tested a door.
    `hypersaw_debug_gesture` calls `Plugin::guiGesture`, which is exactly what
    `hostIf.gesture` calls, so the bracket the oracle opens is the bracket the
    editor opens. Precedent: `hypersaw_debug_capture`, which exists for the
    same reason.
  - *A third bridge verb for the home and the intent names.* Rejected: they
    ride `morphOwnersJson`, which the GUI already fetches for ownership
    colours, under two NON-NUMERIC keys that cannot collide with its decimal
    parameter ids — and they are emitted ONLY while the flag is on, so with the
    flag off that JSON is byte-for-byte what it was. A new verb would have
    meant editing `src/gui/hypersaw_gui.h`, which is out of scope.
  - *Leaving `intentCommit`'s synthetic puck.* Rejected — with a real puck the
    2c identity (`pk = home[dominant]`) stops being an identity: §7's re-home
    onto the puck is what makes the displacement read zero after a commit
    instead of re-applying the offset that was just baked.
  - *Measuring the ADR-152 suspension through `get_value`.* Rejected because
    it MEASURED WRONG: a routed destination's readback is the modulation BASE
    by construction (ADR-136's intercept), so `get_value` reported "no
    movement" for a route that was demonstrably in the table. TS renders
    instead.

- **Open questions:**
  1. **`authorCorners` + morph ON renders SILENT, at flag 0 and at flag 1.**
     Measured while TS's own "not silence" anchor fired on arrival: a patch
     authored by `intent_check`'s `authorCorners` and rendered with the morph
     on measures rms EXACTLY 0, because that helper sets every continuous slot
     to 0.30–0.75 of its range and for `attack` (0.001–2 s) that is 0.60–1.50 s
     — longer than `render()`'s ~1 s window, so the amplitude envelope never
     opens (proved by exempting the slot and shortening it: rms 0.0500).
     **This bears on section S3e**, whose conclusion — "a second writer beside
     morphStep would NOT be harmlessly overwritten" — rests on comparing
     `renderPatch(morphOff, plant)` against `renderPatch(morphOn, plant)`;
     the second of those is one of these silent renders, so the comparison
     cannot distinguish "the plant is audible with the morph on" from "the
     morph-on render is silent". S3e is GREEN and out of this brief's scope
     (it is 2b's), so nothing here changes it — but the 2c decision it
     justified deserves a re-derivation. TS sidesteps it by leaving the
     corners at their defaults.
  2. **A macro knob and the pad are the same pointer.** With the flag on,
     grabbing Macro 1's knob moves the puck exactly as grabbing the pad's x
     does, because the bracket is on the PARAMETER. That is the honest reading
     of ADR-150 (the MAIN pad IS a macro pad) and it is deliberate, but it
     means the two macros the axes name do DOUBLE DUTY: they are the pointer
     AND their own M-intent. Whether ADR-150's assignment should default to
     "None" under the bus — so the performance pad has axes of its own — is an
     ADR candidate.
  3. **Host automation of a pad parameter is fought by the spring.** A host
     that writes macro 1 without a gesture bracket moves the pointer but not
     the drag state, so the puck springs home and the displacement reads zero.
     This IS §4.4's behaviour for a spring-loaded performance control (the
     pitch wheel's shape), but it is a behavioural consequence of the flag on
     two ids that were plain macros before it. ADR candidate.
  4. **The GUI's home marker repaints on `xyDirty`**, which is set by any GUI
     param write — so a morph moved by the GUI moves the marker, and a morph
     moved by host automation alone does not until the next paint that is
     dirtied for another reason. Cheap and consistent with the rest of the pad
     painter; named rather than fixed.
  5. **Two new debug doors** (`..._gesture`, `..._intent_puck`) and one query
     (`..._intent_homeowner`), each with exactly one caller and no shell, GUI
     or host path. `..._gesture` is not a calibration door — it is the
     editor's own verb made headless — but it is new exported surface, which
     2c's open question 4 already flags as a growing count.
  6. **`intent_check` remains STANDALONE and unwired** (2b/2c's open question,
     unchanged): ADR-171 is the route, and wiring a gate into `./verify` is
     the human's decision. Its `feature_tests.tsv` rows still read
     `oracle = none`.
  7. **`rtsafety_probe` is GREEN but still does not drive the flag on.** The
     pad adds no allocation by construction — `padStep` is arithmetic over a
     `Puck` that lives in the Plugin, and `intentNoteGesture` writes two bools
     — so allocation-freedom on the 2d path is ENTAILED, not MEASURED.

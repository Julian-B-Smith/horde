# b151-pan-grid-2 — pan motion onto the gravity grid, as a PAIRED edit to the SAW reference and the core

- **Queue item:** B151 (a), second attempt. The first attempt
  (`traces/2026-09-18-b151-pan-grid.md`, PR #651) was a grounded refusal plus a
  measurement; ADR-177 §1 opened the protected-path gate this needed.

- **Why:** Pan motion (ADR-064) integrated once per render call, which made a
  render depend on the host's buffer size. ADR-086 had already bought the cure —
  a fixed grid of 256/44100 s, interleaved with the audio — for gravity, but
  applying it to pan motion in the C++ core alone costs L0-1 parity, because
  every golden regenerates from `reference/swarmsaw.html` and that file computed
  pan motion per call. ADR-177 §1 (human, 2026-09-19) sanctioned the one
  reference edit, so the two move together and parity holds by construction.

## The defect, stated precisely — the obvious reading is wrong

The per-call form was `dtB = outL.length / sr`, and the tempting summary ("small
buffers swept the image faster") is false: the per-call advances sum to
`rate x total/sr` however the buffer is cut, so the LFO's **rate in Hz was
already block-independent**. What depended on the buffer was the **zero-order
hold** — the pan gains were sampled once per call and frozen across it, so the
staircase was 23.220 ms at 1024 frames and 2.902 ms at 128. Same curve,
different sampling instants, therefore different samples. That is what
`subdiv_check` measured as 0.1915 at chunk 333 and declined to gate. It is now
a 5.805 ms hold whatever the host sends.

The first attempt's comment in `swarm_core.h` and my own first draft of the
reference comment both said "four times faster", and both were wrong; the
measurement (scratch `pan_char.mjs`, the extracted core driven at both
cadences) is what caught it. Recorded because a wrong *why* in a protected
reference is a spec error, not a typo.

## The reference cadence

**256 frames at 44.1 kHz, and it is measured, not chosen.** The first attempt
established it: driving the *unmodified* reference in 256-frame sub-blocks
inside the parity protocol's 1024-frame note-off cadence reproduced the C++
grid build **bit-identically, rms = 0.000e+00 on all nine** pan scenarios. This
edit makes the reference do that by construction — `grid = Math.max(1,
Math.round(sr * 256 / 44100))`, a fixed TIME (ADR-086 A1) so it is exactly 256
at 44.1 kHz and does not shrink as the rate rises.

## What changed

- `reference/swarmsaw.html` (the ONE sanctioned edit): `SwarmSynth.render()`
  becomes the DYN-shaped grid loop (`reference/swarmdynamics.html:420-425` is
  the shape), the body moves verbatim into `renderSeg()`, and the pan block
  moves into a new `advancePanMotion(frames)` called at the top of each grid
  period. Two constructor fields added (`gravAccum`, `panMotionOn`). This
  engine carries no gravity term — here the grid exists for pan motion alone,
  and it is deliberately the *same* grid because the port segments on it.
- `src/swarm_core.h`: `advancePanMotion(frames)` moves from the top of
  `render()` to `if (gravAccum == 0) advancePanMotion(grid)` inside the loop
  that was already there for gravity. Five lines, no second clock, no new
  accumulator. ADR-009 needed nothing: the rates (`0.1`, `0.08 + i*0.021`) were
  already per SECOND and `dtB` is seconds, so the cadence moved and the
  integrand did not.
- `tools/subdiv_check.cpp`: the pan-motion exclusion REMOVED (all four cases
  gated at 0.0 exactly), chunks 1 and 7 added, two controls added.
- `tools/blocksize_check.cpp`: the `gated` flag removed; all eight rows gated.

## The goldens that moved

Nine of 156 — the pan-motion scenarios and nothing else. Measured by rendering
the corpus on `origin/main`'s reference, snapshotting it, and diffing the
regenerated corpus byte-for-byte.

| golden | rms delta | max sample delta | vs golden rms | character |
|---|---|---|---|---|
| `centre-pin.seed{1234,777,42}` | 6.119e-04 | 8.993e-03 | 0.77 % | largest: the centre pin scales the offset by focus distance, so the finer cadence compounds with `driftMode 1` |
| `pan-drift.seed{1234,777,42}` | 2.402e-04 | 1.990e-03 | 0.31 % | seven independent per-voice LFOs, resampled 4x finer |
| `pan-sweep.seed{1234,777,42}` | 1.515e-04 | 1.388e-03 | 0.19 % | the single shared sweep, same |

All three seeds of each scenario move by the identical amount, because these
patches never draw the seeded `grng` stream (the same conditional reach
`blocksize_check`'s control comment characterises).

**The other 147 are byte-identical** — not "within eps", identical bytes,
asserted by the diff above. Structurally so: `panMotion <= 0.001` makes
`advancePanMotion` a no-op that only clears `panMotionOn`, and the segmentation
itself is transparent (the per-segment `tick` advance, soft clip and
`lastPhase` snapshot all compose over segment boundaries).

**Character: smoother, not coarser.** The pan-gain staircase updates at
172.27 Hz instead of 43.07 Hz (hold 5.805 ms, was 23.220 ms) and each step
shrinks about 4x:

| scenario | max gain step before → after | mean step before → after |
|---|---|---|
| pan-drift | 1.252e-2 → 3.130e-3 (4.00x) | 3.597e-3 → 9.016e-4 (3.99x) |
| pan-sweep | 6.767e-3 → 1.692e-3 (4.00x) | 2.511e-3 → 6.296e-4 (3.99x) |
| centre-pin | 9.617e-2 → 4.352e-2 (2.21x) | 6.243e-3 → 1.578e-3 (3.96x) |

centre-pin's *max* ratio is only 2.21x because its largest steps come from
`driftMode 1`'s random-walk re-seats at control ticks, not from the LFO; its
mean tracks the other two. Same trajectory, four times finer.

`parity_check` reads **156/156 within eps=1e-06 (worst 4.262e-09 @
dyn-ring.seed42)**, and all nine moved scenarios read **rms = 0.000e+00** — the
C++ and the JS agree bit-exactly on the new cadence, which is the whole point of
pairing the edit.

## (f) bank / fixtures: NEITHER moved, and that is a coverage finding

No factory patch and no state fixture re-saves or renders differently, so
nothing was regenerated. Evidence: `panMotion` appears 80 times across 40 of the
44 files in `docs/presets/factory/**` and **every occurrence is exactly 0**
(`grep -rEo '"panMotion"[[:space:]]*:[[:space:]]*[^,}]*' | grep -v ':0'` returns
nothing); all three `tests/state_fixtures/*.txt` carry `panMotion=0`.
`bank_check` GREEN (0 failures) and `statefix_check` GREEN (3 fixtures, 0
failures, planted-masterVol control firing on each) on the *unmodified* files.

The honest reading is not "the change is safe here" but "these two oracles were
structurally blind to it" (L0031/L0032): the shipped bank exercises pan motion
nowhere, so a pan-motion regression could never surface in `bank_check`. Left as
an open question rather than fixed, because adding a factory patch is a design
act and out of this brief's scope.

- **Alternatives rejected:**
  - *Make the pan grid 1024 so parity passes unchanged* — rejected by the first
    attempt and not revisited: parity always renders at 1024, so both sides
    would share the subdivision, which is precisely the blindness
    `subdiv_check`'s own header names.
  - *Hoist only the pan block instead of segmenting the reference's render* —
    equivalent for these nine scenarios, but ADR-177 §1 says "segment its render
    … the way `reference/swarmdynamics.html` already does", and only the
    segmenting form survives a future second per-call integrator.
  - *Plant the per-call integrator back into `swarm_core.h` behind a build flag
    for the must-fail control* — rejected: that ships code into the core whose
    only job is to be wrong, and the thing under test is the detector, not the
    core. The miniature reproduces the per-call hold exactly and is paired with
    a grid-cadence twin that must read zero, so it is not an unrelated signal.
  - *Advance pan motion on the 16-sample control tick* (the dispatch brief's
    parenthetical) — not taken: ADR-177 §1 and the first attempt's measurement
    both say the gravity grid, which is 256/44100 s, and 16 would move the nine
    goldens to a cadence the reference measurement never established.

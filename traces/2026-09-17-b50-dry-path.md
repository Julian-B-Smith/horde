# b50-dry-path — the Src→OUT dry path, the pane's top padding, and the rail-persistence defect

- **Queue item:** B50 "PHASE 1c — RANGES AND THE DRY PATH" and the "DEFECT
  (human 2026-09-17, in the plugin)" paragraph above it. The range half of 1c
  was RETRACTED by the human ("I think I was misunderstanding the interface
  when I commented on the negative values coming out of SRC. That seems
  copacetic. SRC to OUT should still be viable though."); no range was touched.

- **Why:** A source could reach OUT only *through* a slot, so a fully bypassed
  rack was not expressible as an edge — which contradicts ADR-088's own premise
  that bypass IS an edge property (a coefficient of 0 *is* "not connected").
  Plus two pane defects the human reported the same day: the matrix's top
  padding, and the rail's ribbons vanishing at rest.

## What changed

**(b) The dry path.** `routing_core.h` gains `srcOut[NSRC]`; the terminal sum in
both `process()` and `processBlock()` becomes
`y += Σ_t outAmount[t]·slotOut[t] + Σ_s srcOut[s]·src[s]`, and `setSerialChain()`
zeroes it. Shell: kind `kRoutingSrcOut` at **22000 + src** (append-only, recorded
in the id-layout comment), name `Out Src%d`, key `rt.srcout.%d`, the **same 0…2
range the out amounts already have**, default 0, continuous so it classes
morphable (ADR-173), appended to the table **last** so it enters `morphIds` after
the whole phase-1 routing block. The `routing` chunk and `morphIds` ride the
existing `g_routingTable` loops, so persistence needed no new code. GUI: the
well's OUT column now exists in the Src rows; the rail draws a Src→OUT ribbon
arced like the other skip edges.

*The aliasing decision worth recording:* in `processBlock` the dry term
**initialises** the output rather than being added to a zeroed one. `outL/outR`
may alias a source buffer (the shell passes the mix bus as both), so a
zero-then-add pass would clear the samples it then reads.

**(c) Top padding.** `#mxBody { margin-top:8px }` (the 8px the pane's own
`.note` already uses below the body) and `#mxWell { padding:9px }` (was
`8px 9px 9px`; the top now matches the sides and bottom it already had). Cascade:
h2 `margin-bottom` 6 + body 8 + well 9 = **23px**, against 6 + 0 + 8 = **14px**.
No new spacing number entered the sheet.

**(d) Rail persistence.** `mxDrawn` — the signature of what the rail last
*landed* — plus `drawMatrixGraph()` returning whether it painted, and a
MutationObserver on `#pg-FX`'s class.

## The (d) paint sequence, traced before fixing (the brief required this)

**The brief's suspect was wrong in its mechanism.** It proposed that "the
bridge's bulk parameter push after a gesture ends … is not among its triggers".
It *is* one: `syncFromEngine` → `paintLive` → `setControl` → `paintControl` →
`paintMatrixCell` → `mxInvalidate`, for every routing id whose value **changed**
(gui2.html:3497-3503, 2173, 6318-6323). And nothing repaints on a gesture *end*
either — `hzGesture` only calls `host.gesture`
(`src/gui/hypersaw_gui_common.h:410-415`); it pushes no parameters.

The actual sequence, then reproduced by a harness rather than reasoned about:

1. The FX page is **hidden at boot** (MAIN carries `.on`), so the first paint —
   scheduled by `buildMatrixPane` on the first poll — reaches `drawMatrixGraph`
   with `clientWidth` 0 and returns without drawing.
2. The guard was `if (mxRaf) return` **alone**, so that one frame *consumed* the
   request and nothing recorded that the rail had never been painted.
3. On reveal, `paintLive`'s `lastPainted` cache (gui2.html:3489-3491) skips every
   routing id because nothing moved, so the bulk sync reaches `setControl` for
   none of them and the rail is never invalidated again.
4. A **drag** repaints it (`paintMatrixCell` → `mxInvalidate`) — exactly "they
   come back only while you're editing them", and exactly why a `file://` load,
   where the page is visible when the pane is built, could not reproduce it.

The asymmetry that lets step 3 bite: the tab handler repaints the gviz set **by
name** on reveal (`drawEnvelope` / `drawScatter` / `drawBendStep` /
`drawBendVib` / `drawShapeWave`, gui2.html:3741-3743) for the documented reason
that a canvas measured while its page is `display:none` has no size — and the
rail is the one canvas left out of that list, leaning instead on a
ResizeObserver that this same file records as undependable in some hosts ("the
measured preview browser fires none at all").

**Harness control** (`mxrail_probe.mjs`, scratch — see Open questions). The mx
block is executed in a `vm` against a stroke-recording canvas, ResizeObserver
deliberately absent, `paintLive`'s `lastPainted` cache modelled. Same probe,
both revisions:

| sequence | before | after |
|---|---|---|
| A built visible, first paint | 5 | 5 |
| A at rest after a bulk sync | 5 | 0 |
| B gesture repaint | 5 | 5 |
| B after gesture → bulk sync | 5 | 0 |
| **C revealed, then a bulk sync** | **0** | **5** |

The two zeros that appear are the signature doing its job — the canvas already
holds that drawing. The 0 → 5 on C is the defect and its fix. *Calibration note:*
the probe's first draft omitted the `lastPainted` cache, called `setControl` for
every id every poll, and therefore **passed on the unfixed file** (5 strokes on
C). A probe more generous than the code under test certifies nothing — L0032.

## Alternatives rejected

- **Adding `mxInvalidate()` to `syncFromEngine`** — the brief's literal "on every
  paint of those cells". Rejected: that line is outside `#mxPane` (the scope
  note), and it is unnecessary — the per-cell path already invalidates on every
  changed value; what was broken was the *dropped* paint, not the trigger.
- **A second reveal trigger in the tab handler** (a sixth name beside
  `drawShapeWave`). Rejected on scope for the same reason; the MutationObserver
  keeps the trigger in the mx block and reuses the mechanism that block already
  uses for the theme.
- **Zero-then-add in `processBlock`** — rejected on the aliasing hazard, and the
  rejection is *measured*: planted, assertion 14 fires 1023/1024 and the
  0.5-gain control collapses to 1/1024.
- **Regenerating the factory bank** to clear `bank_check` — out of scope (see
  below), and it is a human ruling, as it was for PR #607.

## Open questions

1. **`bank_check` needs a human ruling**, the same one PR #607 got: regenerate
   the 40 factory patches so their corner arrays carry the new slot, or hold the
   morphable classification of `srcOut`. Nothing here can clear it in scope.
2. **The harness control for (d) is not wired.** The brief authorised creating
   only this trace file, so the probe lives in the session scratchpad
   (`.../scratchpad/b50-1c/mxrail_probe.mjs`). Landing it as a gate needs a new
   `tools/labharness/` file and a `./verify` line — both out of scope.
3. **No screenshots.** This dispatch had no browser-automation tool, so (c) is
   evidenced by the cascade arithmetic rather than by a render. Both revisions of
   the real file are preserved in the scratchpad for a side-by-side open.
4. **The (c) reading is an interpretation.** "The inner top spacing the other
   clusters' data wells use" names no existing token — `#mxWell` is the only
   `var(--well)` box in the sheet. The two numbers chosen are the pane's own
   (its `.note`'s 8px, its well's 9px); if the human wanted a different
   quantity, it is one line.
5. **ADR candidates** (not filed — `DECISIONS.md` is out of scope):
   *(a)* the dry path as the fourth routing kind at 22000, and the rule that the
   OUT column carries one range for both its kinds; *(b)* `processBlock`'s dry
   term initialises rather than accumulates, because the output may alias a
   source — a constraint any future terminal contribution inherits; *(c)* a
   canvas painter that can be asked to paint while its page is hidden must
   report whether the paint *landed*, and the invalidator must key on the last
   landed state rather than on a pending-request flag.

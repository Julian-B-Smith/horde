# b549-chain-line-offset-bars — the Design System's Chain line: dots are read-only again; each stage's gain is a fixed vertical offset bar in a gain lane under the line

- **Queue item:** ROADMAP B549 (ADR-272 A1; the human on B547: "right now it's a little confusing since the dots move on their own so it's unclear where they end up. Maybe the control should appear as vertical offsets and not move with the shape"). Written by the implementer for the lead, who lands it in `traces/` (every file of the horde repo was out of scope, so this draft stays in the scratchpad).
- **Why:** a dot that is both the moving reading and the gain handle is the confusion. The dots return to being measures (pointing and naming kept). Each stage's gain is its own control: a bar from a 0 dB baseline in a lane under the line, in the stage's own dot column, that moves only when dragged or when the model moves. The model is unchanged from B547: the line holds no gain, takes `gain(id)` / `onGain(id, dB)`, and a fader and a bar read one value. Gain staging's code did not change (`50-ring-gain.js` identical, `cmp`).
- **Evidence consulted:** the B547 trace and its scripts (`b547-impl/`, adapted into `b549-impl/`); `60-chain-blend.js` / `.css`; `50-ring-gain.js` (drag law :211-214, key step :219, `setGain`/`gain` :297-299, `chain()` ranges :169-188); `00-core.js` `Viz.kit` (:644, canvas sized to its CSS box) and `00-core.css` `.hd-slider` / `.hd-viz` (the house handle, track and glass); `tokens.json` (stroke-ink 1.5 px, size-hit 28 px, shadows, focus-ring).
- **Removed (B547):** dot dragging, the held-dot handle and its boxed readout, the fan-out (hover, key and touch fan, `dx`/`name`), the settle (`off`, `SETTLE_S`, reduced-motion branch), `touch-action: pan-x` on the glass, the "held" key swatch, the double-role caption, the `grab`/`held` fields of the painter. **Kept:** pointing and naming (hover, tap, ← →, `probe()`), the readout (it still names the stage's gain), the peak-hold law, the rings, the labels, the key.
- **Built (`60-chain-blend.js` / `.css`):**
  - **Layout.** Every tap has its own slot, in order: the dot of tap k is at the centre of slot k, and the lane's grid puts the bar of tap k in the same slot (canvas and lane share the 38 px / 10 px margins and the same border and box-sizing, so the columns agree to 0.01 px, `behave.log`). The four sources therefore sit side by side in the first column (dots and bars both), 43.9 px apart at 960 px; no fan is needed.
  - **Bar.** A rail spanning the stage's own range (`stage.gain`), a `value` fill from the baseline to the handle (rises for boost, falls for cut), a tick at 0, the house handle (`panel`, ink outline, rest/hover/pressed shadows; `value` while dragging; focus ring on the handle), the dB value on a `well` chip beside the handle on its free side (above for 0 and boosts, below for cuts; on the chip so the rail does not strike through it). The make-up's default +12.04 dB is an 18.9 px standing bar.
  - **One scale.** The lane's dB scale is the union of every stage's gain range with 0 (instrument chain −60 to +24 dB; 168 px lane, 18 px inset at each end for the labels), so equal dB is equal height: px per dB is 1.571 on f1i (−24..24), eng (−60..12), mk (−12..24), osc1 (−60..6), and f1i and eng at the same dB have the same bar height and handle y. 0 dB, +24 dB and −60 dB are labelled in the gutter; a hairline marks 0 across every slot, empty ones too.
  - **Gestures.** Relative vertical drag, 160 px = the stage's whole range, shift ×0.25, an unclamped hand (value cannot drift from the pointer), double-click sets `stage.gain.def`, ↑ ↓ on a focused bar 1 % of the range, shift 0.25 %, gated by `keys` (default on; `keys` off also drops the bars from the tab order, like Gain staging's faders). `role=slider`, `aria-orientation=vertical`, valuemin/max/now/text. Pressing a bar writes nothing.
  - **Reading only.** A bar redraws only when the value it reads has changed, and it reads `gain(id)`; the levels animating never touch it.
  - **Phone width.** A slot is at least 32 px (house floor 28), set in CSS as `min-width: calc(48px + var(--cl-n) * 32px + ...)` on `.cl-inner`; where that exceeds the card (20 slots = 691 px), the glass and the lane scroll sideways TOGETHER in `.cl-scroll`, so a dot and its bar never part and the page does not scroll sideways. The bar is `touch-action: pan-x` (a horizontal pan scrolls, a vertical drag is the gain); the glass is default again (it is no longer a control). A line built without `gain`/`onGain` has no lane and no forced width (B545 behaviour).
  - Colours are tokens only (`value`, `ink`, `well`, `well-alt`, `panel`, `t2`, `hint`; the glass keeps the screen roles). No `Math.random`, no wall-clock read.
- **Alternatives rejected:** the value label inside the handle (a pill handle as wide as the slot: a different handle from the house one); the label at the side of the handle (a 32 px slot has no room beside a 13 px handle: it travels along the bar's axis, on its free side); a lane scale from the single widest span (72 dB, eng) (the make-up reaches +24, so it would overflow; the union is the only scale on which every bar fits and equal dB is equal height); only the lane scrolling (the dots would part from their bars); stacked source dots with side-by-side bars (the eye link would break for the sources); bars as canvas drawing (a control wants real focus, keys, aria and pointer capture: DOM); pointing at a dot from a bar's hover or focus (a behaviour nobody asked for).

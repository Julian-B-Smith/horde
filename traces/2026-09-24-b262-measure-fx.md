# b262-measure-fx — what every rack FX module costs, and what the missing ones will

- **Queue item:** B262 (row carried in PR #746, `lead-records-86`; dispatched 2026-09-24 by the horde lead). Human, verbatim: "Let's definitely run a cost bench, keeping in mind that some FX haven't been created yet (we don't have a proper compressor or multiband compressor or EQ yet, or real filters built, etc.)". This is the budget the patch-model question (B263 — how many FX racks a patch may run at once) needs.
- **Why:** B263 cannot be answered without knowing what a rack (and several racks, per the corner-bus idea) actually cost against the engine's own CPU budget, and what the FX types the human wants but that do not exist yet (EQ, compressor, multiband, real filters, reverb, MAW) would add once built.

## What was done

New `tools/measure_fx.cpp` (UNWIRED, same standing as `measure_alias`/`measure_cpu`/`measure_modsources`: prints, never judges — see its own header), wired into `CMakeLists.txt` as a standalone `add_executable` beside `measure_modsources`, linked against `${PROJECT_NAME}-impl` (needed only for the one engine-baseline cell that drives the CLAP factory; every FX-module cell talks to `hypersaw::FxRack` directly — it is header-only, so no plugin shell is needed to reach it, which is the "reduce, never invent" reading of the brief's "reuse measure_cpu's method").

**MEASURED, in C++** (`tools/measure_fx.cpp`, Release `-O3`, `build-bench`, 5 s audio-equivalent per cell, min of 3 reps, calibration `min of 3 = 153.23 ms` against measure_cpu.cpp's own recorded quiet baseline of 147.0 ms — 4.2% over, well inside its 35% "machine busy" cutoff, so the run is a real measurement): each of the rack's nine module types (`kFxTypeLabels`, `src/hypersaw_clap.cpp`; `FxType`, `src/fx_rack.h`) in one slot, at 44.1/48/96 kHz, at default and at the module's most expensive REACHABLE setting (read out of `fx_rack.h`/`time_core.h`/`delay_core.h`/`notch_core.h` — see the per-`setup*()` comments in the file for what "worst" means for each and, for Notch and Delay, why there ISN'T a rack-reachable setting more expensive than default); a full 4-slot rack at a measurement-picked worst combination and at a plausible typical combination; and the engine's own baseline via measure_cpu.cpp's own method (CLAP factory, 8 held notes, 128-sample blocks, 44.1 kHz, n=8 voices/note, 1 osc — one of measure_cpu.cpp's own five audited cells, re-run here rather than hardcoded so the number is live against this build).

**PROJECTED** (Node, scratch scripts under the session scratchpad — not committed, per the brief's own split between the C++ "DELIVERABLE" and the trace/PR-body "OUTPUT"): EQ and compressor (`docs/design/fx-design-lab.html`'s B234 cards, `EqDSP`/`CompDSP`), a multiband compressor (no lab exists — analytical, 3-band crossover + 3×`CompDSP`), the filter swarm bank (`reference/swarmfilter.html`'s `FilterLab`, the class `docs/design/filter-lab.html:410-417` names as what the rack-side filter lab injects), the reverb FDN (`docs/design/reverb-lab.html`'s `SwarmVerb`), and MAW (`reference/maw/core.js`'s `MawCore`, which already ships its own Node CPU-timing convention in `reference/maw/fidelity.js` §5c — this bench's MAW measurement follows that same shape).

## A correction to the brief's premise: B236 has no JS→C++ ratio

The brief asks to "apply the JS→C++ ratio seen in B236" for the PROJECTED numbers. Checked: `grep -n ratio traces/2026-09-23-b236-measure-modsources.md` and the ROADMAP B236 row itself — neither records a JS→C++ timing ratio. B236 measured ORBITAL/Kuro LFO **in C++ only**, with a **bit-parity diff** against the JS (max|Δ| 0 for Kuro, 6.14e-6 for ORBITAL, both root-caused), never a JS timing. There is no ratio to reuse.

So this dispatch derived a fresh one, grounded in this repo rather than assumed: `scratchpad/b262/js_cpp_ratio.mjs` times `PhaserLab.chain()` (`reference/swarmphaser.html`, the JS source `notch_core.h` was transcribed from) and `TimeLab.processSample()` (`reference/swarmtime.html`, `time_core.h`'s source) headlessly in Node via `tools/golden/extract_core.mjs`, at the SAME band counts `measure_fx` had just measured in C++, so each pair is a real same-algorithm comparison:

| pair | JS ns/sample | C++ ns/sample | ratio |
|---|---|---|---|
| Notch, nb=6 | 121.2 | 48.5 | 2.50x |
| Echo, nb=8 (default) | 182.2 | 76.5 | 2.38x |
| Echo, nb=12 (worst) | 242.3 | 91.8 | 2.64x |
| Room, nb=8 (default) | 291.5 | 110.1 | 2.65x |
| Room, nb=12 (worst) | 410.2 | 152.1 | 2.70x |

Mean **2.57x**, range 2.38–2.70x. Node's own calibration loop (same fixed FLOP loop as `measure_fx.cpp`'s) read 329.7–336.8 ms across all three Node scripts in this session — stable across them, so the machine's relative load did not swing mid-session even though the JS/C++ calibration figures are not directly comparable to each other (different runtimes; V8 vs native). **Assumption stated plainly: this dispatch uses 2.57x as the JS→C++ conversion factor below.** It is a same-day, same-machine, same-algorithm measurement, not an inherited constant — a future re-run should re-derive it rather than hardcode 2.57.

## Verdict

**At default/typical settings, every existing and projected FX module is cheap** — the most expensive single default cell measured or projected is the Reverb FDN at 0.885% of one core, and a full typical 4-slot rack is 0.096%. Even the engine's own recorded worst case (2-osc, n=32, 14.15%) plus four WORST-settings racks (using only the module types that ship today) totals under 20% of one core.

**The one real outlier is MAW at aggressive oversampling across all three stages**: 9.7% of one core PER INSTANCE at 3 stages / 8x oversample. Four of those (one per morph corner, per B263's proposal) would be ~38.8% of a core from MAW alone, before the engine or any other FX. This is not a blocker — 8x/3-stage is MAW's own stated worst case, not its default — but it is the one module where the patch-model decision (B263) should either cap oversampling per corner or accept that a "4 racks, each running a maxed-out MAW" patch is the CPU ceiling to test against, not the common case.

**What the numbers allow, plainly:** the engine + FX racks are 5–10x cheaper, per rack, than the difference between a light and a heavy VOICE load already is (14.15% vs 0.54% at the extremes of `measure_cpu`'s own table). One rack is free. Two racks (a left/right morph-corner bus, B263's crossfade idea) cost about as much as going from n=1 to n=4 voices on ONE oscillator — negligible. Four racks (one per corner) cost about as much as going from n=8 to n=16 voices — still comfortably inside the audited engine's own headroom, PROVIDED oversampling-heavy modules like MAW are capped rather than left at their worst default per corner.

## Alternatives rejected

- **Hardcoding a JS→C++ ratio from B236.** Rejected because it does not exist there — see the correction section above. Deriving a fresh one from same-algorithm pairs already in this repo (Notch/Echo/Room, both JS and C++) is more grounded than inventing or guessing one.
- **Driving `FilterRig`/the full per-voice filter lab instead of `FilterLab`'s bank.** `docs/design/filter-lab.html`'s `FilterRig` is a small polyphonic synth (8 voices × up to 3 SVFs + an injected swarm bank) built to audition PLACEMENT (pre/post, per-voice vs bus), not the bank's own per-sample cost in isolation. Timing the injected `FilterLab` bank directly (the class `filter-lab.html` itself names as the thing it injects) measures the actual swarm-filter algorithm without the lab's own voice-management scaffolding inflating the number.
- **Embedding the PROJECTED Node timings inside `tools/measure_fx.cpp`.** The brief separates the C++ "DELIVERABLE" (MEASURED) from the trace/PR-body "OUTPUT" (PROJECTED, "clearly labelled as projections, never presented as measurements") — folding Node calls into a CMake C++ target would also be a new build dependency this repo's benches don't currently carry (`measure_modsources.cpp`'s own header explicitly rejects adding a Node dependency to a C++ benchmark for the same reason). Kept as scratch scripts instead.

## Open questions

1. The multiband compressor row is the weakest number in this trace (analytical crossover cost, no lab, no direct timing) — if B263 or a later dispatch needs a tighter number, building even a throwaway 3-band crossover JS lab would replace an estimate with a measurement.
2. Whether MAW ships with a per-corner oversampling cap (the one module whose worst case is not negligible) is a decision for whoever builds it, not this dispatch — flagged in the verdict, not resolved here.
3. The JS→C++ ratio (2.57x, range 2.38–2.70x) is this session's own number on this machine; a future re-run for a different decision should re-derive it rather than treat 2.57 as a constant.

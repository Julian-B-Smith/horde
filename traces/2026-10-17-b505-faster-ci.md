# b505-faster-ci — the ASan+UBSan oracles run in parallel; CI's thread job runs tsan_stress_check

- **Queue item:** ROADMAP B505 (ADR-233, the human 2026-10-17: "Go ahead with 1 and 2"). Acceptance: "a CI run on the PR in which the ASan+UBSan job runs every oracle it ran before, the same count passing, in clearly less wall time (target ≤ 20 min); the thread job either runs `tsan_stress_check` green with its must-fire control, or is removed with the evidence why; and `./verify fast` is green." Brief: the horde lead, 2026-10-17 (records PR #1119, branch lead-records-273).
- **Why:** CI run 38991514882 took 43 min, almost all in the two `sanitize` legs, which ran 54 oracles one at a time on a 4-core runner; and the TSan leg could never fire, because no oracle starts a second thread (ADR-233's finding).
- **What changed:**
  - `tools/sanitize_oracles.sh`: the oracles run `NPROC` at a time through `xargs -P` (bash 3.2 safe: no `wait -n`, no arrays in the runner). Each writes its own `$BUILD/<name>.sanitize.log` and a `<name>.sanitize.rc` (exit code and seconds). Verdicts print in ./verify's order after all finish, in the old PASS/FAILED shape, with the full log for a failure. A missing `.rc` is red. The five slowest oracles launch first. A closing line gives the batch wall time and the slowest five. The summary line, the `rtsafety_probe` NOT RUN line and the not-built SKIP lines are unchanged. The build stage is unchanged.
  - `SANITIZE_ONLY="a b"` builds and runs only the named oracles. It is a documented local aid and is refused under CI (`CI` set means exit 1 before configure). Every line it touches says SUBSET.
  - `.github/workflows/ci.yml`, the `sanitize` job only. The matrix keeps both names, so the check names `sanitize (address,undefined)` and `sanitize (thread)` stay. The address leg runs the script as before. The thread leg runs `python3 tools/tsan_stress_check.py build-tsan-stress` with `HORDE_SANITIZER_CXX` set to the runner's g++, the compiler CMake configures the impl with, whose `flags.make` the check reads. The step fails if the check prints SKIPPED, which it does with exit 0 when it finds no TSan compiler.
- **Shared paths found (each oracle source, the headers they include, and the node scripts the h2 parity checks popen):**
  1. `endprobe` and `trace_check` both press PANIC. That writes `$HOME/<store>/logs/panic-<trace counter>.txt`, and trace_check reads its dump back. Confirmed locally: both wrote `panic-10.txt`, which would have been one file under a shared HOME.
  2. `preset_pitch_check` and `presetstore_check` use fixed directory names under the temp dir. The two names differ, so they do not collide today.
  3. `gui_webview_check` and `identity_store_check` use `mkdtemp`, so their names are unique. Both are macOS-only.
  4. `h2_engine_selfdigest_check` writes its reference only under `--repin`, and `h2_harness_render` writes only with `--out`. The script passes neither.
  5. The golden dirs are written by the generators before the batch and only read during it.
  6. No oracle reads stdin unless given `-`, and none is.
  - **Resolution:** every oracle gets its OWN `HOME` and `TMPDIR` under `$BUILD/sandbox/<name>/`, plus `stdin </dev/null`. No oracle's logic changed.
- **Thread job, Linux feasibility (by reading, not run on Linux):**
  - The harness is one TU that includes `src/hypersaw_clap.cpp`.
  - The shell's only platform-gated code is the GUI extension and the editor teardown (`#if defined(__APPLE__) || defined(_WIN32)`). The harness calls none of the 15 gui_* functions.
  - The script adds the GUI object and frameworks only on darwin, and `-isysroot` only on darwin.
  - On Linux, HYPERSAW-impl is the shell alone; the existing sanitize job already builds it there.
  - Hypothesis until the PR's CI run shows it: the thread leg builds and runs green on ubuntu-latest.
- **Evidence consulted:**
  - `tools/sanitize_oracles.sh`, `tools/tsan_stress_check.py`, `tools/tsan_stress.cpp` (header).
  - `src/hypersaw_clap.cpp`: `writeForensics`, and the `__APPLE__`/`_WIN32` blocks at 10035, 10684–11284 and 11306.
  - `src/gui/preset_store.h` `presetRoot`.
  - The oracle sources per `CMakeLists.txt` `add_executable`.
  - `tools/weakening_check.py`, `tools/build_flags_check.py` and `tools/armor_coverage_check.py`: what they read of the script and the workflow.
  - ADR-233 and B505 on lead-records-273.
- **Local evidence (macOS, scratch build dirs outside the repo):**
  - With Apple CLT, every ASan binary dies at init (`AddressSanitizer: CHECK failed: sanitizer_malloc_mac.inc:189 ... asan_init_is_running`), run directly as well as through the script. This is the ADR-199 class of runtime failure and not this change. The runs below used Homebrew clang++ for C++ and Apple clang for the ObjC GUI object.
  - Subset of 8 plus `rtsafety_probe`: GREEN, 8 passed, rtsafety_probe NOT RUN, 18–19 s wall on 8 jobs.
  - The same subset with `delay_check` replaced by an ASan heap-overflow plant and `svf_check` by `exit 7`: RED, exit 1, "6 oracle(s) passed". Both failures were printed with their full logs, in ./verify order.
  - `CI=true SANITIZE_ONLY=…`: refused, exit 1.
  - `tsan_stress_check` on this tree (Homebrew LLVM): GREEN in 271 s including its build. Plant: 1 WRITE. Plant-read: 1 READ, 0 WRITE. Control: 0 reports on all three seeds. Full: 0 main-thread WRITE and 0 unattributed on all three seeds.
- **Alternatives rejected:**
  - Running endprobe and trace_check serially after the batch. It fixes the one collision found, but not the next oracle that writes under HOME or the temp dir.
  - Parallelising the per-target build. Concurrent make invocations in one build dir race on shared generated headers, and the brief did not ask for it.
  - Using clang++ for the thread leg. The impl's `flags.make` comes from the g++ configure, and g++'s TSan is the one this runner has already run.
- **Verify:** `./verify fast` on the staged tree. The exit code, its closing lines and the `.harness/last-verify.json` tree check are in the hand-back and the PR body. The PR's own CI run is the second half of the verify target and is the lead's to read.
- **Open questions:**
  - `docs/armor/catalogue.json` R2's gaps text says "CI runs neither" (tsan_stress_check, load_handoff_check). That is stale once this merges. It was out of scope here, so it is left for the lead.
  - The serial `./verify` runs `endprobe` and `trace_check` with the real HOME, so on a dev Mac their PANIC dumps land in the user's real store `logs/`. This was not changed and is outside this brief.
  - Whether ASan wall time meets ≤ 20 min is measured only by the PR's CI run.

## Round 2 (same PR, after CI run 39005256368)

- **Why:**
  - The thread leg was GREEN on ubuntu in 2.7 min with its controls.
  - The ASan leg took 38 min against the ≤ 20 min target. The parallel batch took 1208 s (selfdigest_check 944 s, parity 820, selfdigest_product 762, fma_control 752, stability 456), and about 18 min before it went to building the oracle targets one at a time.
  - The lead's brief (round 2) asked for both fixes in one push, within the human's ruling ("run in parallel").
- **What changed:**
  - `tools/sanitize_oracles.sh`, build: ONE keep-going build of all selected oracle targets (`cmake --build -j"$NPROC" --target t1 t2 … -- -k`) into `$BUILD/oracles.build.log`. Built means the executable exists afterwards; each one is deleted first, so a stale binary cannot stand in for a target that no longer builds. A target that fails is reported as before (`DOES NOT BUILD … SKIPPED`), with up to three lines grepped from the combined log by its object dir or source file.
  - `tools/sanitize_oracles.sh`, sharding: `SANITIZE_SHARD=i/n` is allowed under CI and must match `^[1-9][0-9]*/[1-9][0-9]*$` with i ≤ n, or the script exits 1.
    - The seven HEAVY oracles are dealt round-robin, longest first, and every other parsed oracle goes to (its index among the non-heavy) mod n. The shards are a partition by construction, and each builds only its own oracles.
    - Each shard prints `== shard i/n: K of N parsed oracle(s): …`, and its summary line carries `shard i/n of N parsed;`.
    - HEAVY is also the launch order and replaces SLOW_FIRST. `SANITIZE_ONLY` is still refused under CI.
  - `ci.yml`: the matrix is now `include` with address,undefined at shard 1/2 and 2/2, plus thread. An explicit job name keeps the checks readable: `sanitize (address,undefined, 1/2)`, `sanitize (address,undefined, 2/2)` and `sanitize (thread)`. The job id `sanitize` is unchanged, so `release`'s `needs:` is unaffected.
- **Local evidence:**
  - With cmake off PATH, the script stops right after printing the assignment. Shards 1/2 and 2/2 of the full list have 39 + 38 = 77 oracles, no overlap, no duplicates, and their union equals the parsed list.
  - A real two-shard run of an 8-oracle subset gave {delay_check, filter_check} and {presetstore_check, svf_check, trace_check, endprobe, rtsafety_probe, notch_check}, disjoint and covering all 8. Both were GREEN, and rtsafety_probe was reported NOT RUN in its own shard only.
  - Nine malformed values (`0/2 3/2 1/0 a/b 1-2 1/2/3 01/2 " 1/2" 2/2x`) all exit 1.
  - The combined build with a toolchain where endprobe and trace_check cannot link: both were reported DOES NOT BUILD with make's lines from the shared log, and delay_check still built under `-k` and passed.
- **Predicted balance (hypothesis):** the heavy deal is shard 1 {selfdigest_check, selfdigest_product, stability_check, scalpel_fma_control} and shard 2 {parity_check, fma_control, scalpel_parity_check}. Shard 1 carries more heavy seconds, so it is the likely long pole. The PR's CI run measures it.
- **Verify:** `./verify fast` on the staged tree. The result and the tree check are in the hand-back and the PR body.

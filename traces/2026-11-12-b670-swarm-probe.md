# b670-swarm-probe — how far one swarm oscillator can be sped up, candidates 2 to 4 in scratch, and the 1.0 path measured

- **Queue item:** B670 (ADR-396; ADR-392 item 3).
- **Why:** C2a's target (ADR-392 item 4) waits for this probe. ADR-392's baseline put one whole wavetable oscillator at about 18.5 % of an M3 core, about 4x a Serum 2 oscillator (4.6 %).
- **Evidence consulted:** the clean-room engine at e72a092 (`engine2/core/swarm/swarm.cpp`, `blades.cpp`, `blade/spreads.cpp`), exported into a scratch clone outside both clean-room repos; `docs/wavetable/CONTRACT.md` §1.2 (the member blocks a table member keeps, replaces and retires; WT-24: no filter E on a table member); `tools/c2a_remainder` (`--count`, and `--timed` with ADR-391's check); `/usr/bin/sample` on the bench; bank renders of all 83 presets at 128- and 61-sample blocks; the engine's own suite.
- **Who did what:** candidates 2 to 4 and the profile by a pinned Sonnet implementer in the scratch clone (ADR-396 "Split"); the 1.0-path ablation, the timed runs and this reading by the lead. Candidate 1 is the builder's (brief: lead commit `11b8c6f` in the clean-room engine) and is not measured yet.
- **Verify:** `nice -n 10 ./verify fast` on this branch (see the PR). Nothing from the scratch clone enters this tree or the builder's.

## The 1.0 path (the lead's ablation)
Two scratch commits remove what CONTRACT §1.2 says a table member does not run: filter E, the base-wave edges, the spread walk. One on the base (`path10` on e72a092), one on all of 2 to 4 and 3b. It is a floor, not the table member: WT-31's loop tap and xin, WT-25's means and a sync restart's edges are not added, and the table read is WT-BUDGET's estimate, not measured.

**Instructions (cell C, 48 kHz):** base 2264.9 → path 1191.5 (−47 %); per-member slope 188.06 → 66.45 (−65 %); intercept 577 → 594. With 2 to 4 and 3b under it: 1249.7, so on this path they cost 5 % more, not less (candidate 2's two-pass loop with nothing left to batch).

**Timed** (`--timed`, 2026-11-12 from 01:14, Live and verify off, the implementer's suite stopped; both must-fail controls REJECTED on both runs; best of 5 clean repeats; % of one core, 48 kHz):

| | Today's engine e72a092 | 1.0 path |
|---|---|---|
| Cell C, blades off, 9 members | 13.18 % | 5.86 % |
| Remainder, own base (C less idle) | 12.63 % | 5.30 % |
| Remainder, sine base (J less idle) | 13.96 % | 6.81 % |
| Per-member slope | 1.07 % | 0.24 % |
| Per-voice intercept (8 voices) | 3.54 % | 3.75 % |

At 44.1 kHz the same shape: 12.32 % → 5.33 %. Today's figure agrees with B668's 13.5 % (sine base, 13.96 % here).

## What it means
- **ADR-392's 18.5 % per oscillator counted work a table member never runs.** On the 1.0 path the remainder is about 5.3 to 6.8 %, so a whole table oscillator is about 10.3 to 11.8 % with WT-BUDGET's 5 % read: about **2.2 to 2.6x** Serum 2's 4.6 %, not 4x. A floor, until the real member exists (S1).
- **Candidates 2, 3b and most of 3 are moot for 1.0:** they speed up E and the spread walk, which the table member does not run. Candidate 4 gains nothing (the law's trig is 1 % of the cell) and changes bits: drop it. Candidate 3's per-tick hoists are bit-identical and small (about 2 % of the old cell).
- **The per-voice intercept is now about 70 % of the remainder** (3.75 % of 5.30 %): the per-tick settings read and `context()`. That is exactly candidate 1, the builder's.

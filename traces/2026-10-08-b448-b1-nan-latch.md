# b448-b1-nan-latch — the legacy output guard counts and latches instead of zeroing silently

- **Queue item:** B448 Wave B item B1 (ADR-197, Blind-Spot Armor, risk row 3, "Symptom clamping" rule).
- **Why:** B446 added `zeroNonFinite` as the last line before the host bus and discarded its return value, so a non-finite sample was repaired and nobody could ever learn it happened. ADR-197 allows an output safety guard only if it latches and reports. Output is unchanged: the repair is still `zeroNonFinite` (reused, not re-implemented), so no new `isfinite`/`isnan`/clamp was added and the weakening counter reads 0 increases.
- **What changed:**
  - `src/output_latch.h` (new): `hypersaw::NonFiniteLatch`, relaxed atomics (samples replaced, blocks with a hit, latch). Counters are touched only when a block had a hit. The latch clears only via `reset()`.
  - `src/hypersaw_clap.cpp`: `Plugin::nonFiniteLatch` + `Plugin::guardOutput`, the one call site; `process()` ends with `guardOutput(outL, outR, nframes)` where the two bare `zeroNonFinite` calls were. Five `hypersaw_test_*` hooks (declared in `src/hypersaw_clap_entry.h`): samples, blocks, latched, reset, and `hypersaw_test_guard_output` which runs the shipped `guardOutput` on a caller's buffer.
  - `tools/nan_latch_check.{cpp,py}` (new), wired into `./verify fast` right after `embedded_page_policy_check`. Planted NaN (quiet, signalling, negative-with-payload), +Inf, -Inf in left/right/both: zeroed, counted, latched; clean buffer counts 0 and is bit-identical (-0.0, denormal, FLT_MAX); latch survives clean blocks; reset clears; zero-frame block inert. Five must-fail controls (zero-without-count = B446 as shipped, count-without-latch, self-clearing latch, right channel unreported, reset keeps the latch) each fail >=1 row. The .py also greps the shell for the call chain and runs a planted-bare-`zeroNonFinite` control against that grep.
  - `tools/hostile_events_check.cpp` (`./verify full`): LATCH rows. Every hostile-event run must leave the real plugin's counter at 0 (boundary guards stop it upstream; finite output alone could not tell the difference), then the planted buffer through the shell's own `guardOutput` is counted and latched, survives four real `process()` blocks, and is cleared by reset.
- **Audits (report only, nothing changed):**
  - **Flush-to-zero:** ABSENT in `src/` and `h2/`. No `FPCR`, `MXCSR`, `_MM_SET_FLUSH_ZERO_MODE`, `_MM_DENORMALS_ZERO_ON`, `ScopedNoDenormals`, `fesetenv`, `xmmintrin.h`, `arm_neon.h` or `fenv` anywhere (grep over `src`, `h2`). `process()` (`src/hypersaw_clap.cpp:8748`, `plug_process` :9089) sets no FP mode, so the shell runs with whatever mode the host thread has. Instead the cores snap denormals in software: `src/swarm_core.h:1285-1305` (and the h2 copy `h2/cores/swarm/swarm_core.h:1296`) says in its own comment that the min-spec x86 "has no FTZ" and measured 334 subnormal output samples per 30 s tail before the fix; `src/subosc_core.h:185` floors a tone-filter state. `tools/denormal_check.cpp` header quotes the B147 audit: "FTZ/DAZ active in this process: no". No `-ffast-math` in `CMakeLists.txt`. Changing FTZ would alter output (a default change, ADR-197: ADR plus migration), so it is left to the lead.
  - **horde 2 output guard:** NONE. `h2/engine/engine.h:1961-1962` ends the sample loop with `L[i] = std::tanh(yl * s.gain * 1.6); R[i] = std::tanh(yr * s.gain * 1.6);` and a NaN passes through tanh unchanged. The `isfinite`/`isnan` calls in `h2/engine/` are JS-semantics helpers (`h2/engine/js.h:37-66`) and one grain filter (`engine.h:827`), not output guards. There is no h2 shell yet (only `tools/h2_engine_*` consume `horde2::engine`), so an h2 guard is a design question (where it lives, whether it shares `output_latch.h`) and h2's E1 self-digests were not touched.
- **Evidence consulted:** `docs/strategy/blind-spot-armor.md` (risk row 3, symptom clamping rule, decision D); `src/input_guards.h:139`; `src/hypersaw_clap.cpp` process tail; `tools/embedded_page_policy_check.*` (house style), `tools/test_table_check.py` (WIRED rules: declaration must be in the first 40 lines; my first hostile_events_check edit pushed it to line 43 and `./verify fast` went red on test_table_check until trimmed).
- **Alternatives rejected:** exposing the count in the GUI viz struct (`outPeak` in `src/gui/hypersaw_gui.h:62`, JSON in `hypersaw_gui_common.h:103`): that is a GUI feature and a bridge-shape change, out of scope, filed as a follow-up. A poison-the-next-block test hook inside `process()`: adds an audio-thread branch to ship a test; `guardOutput` driven on a caller's buffer gives the same shell-function coverage at no runtime cost. Counting per channel: nothing needs it yet.
- **Not shown:** that a real DSP fault makes `process()` itself count (no real fault is reachable through the boundary guards; the `process()` call is covered by the grep in `nan_latch_check.py`, the counting by `guardOutput` rows). Bit-identity of the shell's output against a pre-change build was not measured with a before/after digest; it is entailed (same `zeroNonFinite`, atomics touched only on a hit) and supported by the clean-buffer bit-identity row plus the shell-level checks below.
- **Verify:** `./verify fast` exit 0 (`.harness/last-verify.json` git 33cd3a4 at the time of the first green run, re-run after commit for the PR). Release build in this worktree, run by hand: parity_check 156/156 (worst 4.262e-09), hostile_events_check GREEN (incl. 6 LATCH rows), state_check, notefuzz_check, sr_check, blocksize_check, denormal_check, rtsafety_probe (audio thread allocation-free), stability_check --seconds=60 all GREEN. `./verify full` was not run end to end.
- **Open questions:** (1) GUI surfacing of the count (follow-up). (2) An h2 output guard and whether it reuses `output_latch.h`. (3) FTZ/DAZ: needs an ADR plus migration if wanted; the shell currently relies on software snapping (hypothesis, not measured here: whether hosts set FTZ themselves).

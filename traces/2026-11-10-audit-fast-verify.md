# audit-fast-verify — verify fast runs its five slow gates concurrently; a skip is recorded as a skip

- **Queue item:** unqueued: the human's poll answers on the independent audit (docs/audits/2026-11-10-fable-audit.md findings 4 and 8: "Faster verify fast", "Skips visible"). The human approved the `./verify` edit on condition that no gate changes its verdict and none is loosened.
- **Why:** `./verify fast` was 4.5 minutes strictly serial, 69 % of it five gates; and `.harness/last-verify.json` had `"gates":[]`, so a gate that skipped and one that judged left one record.
- **What changed:**
  - `verify`: gui3_seam_check, gui3_browser_check, sandbox_check and build_flags_check then stop_gate_check (one chain, one slot) start as background jobs at the top of `fast()`; each job's stdout+stderr goes to its own mktemp file, its exact exit code and seconds to files beside it (the `.rc` is written last, so a killed job has none and reads as failed). They are waited for one PID at a time at the END of `fast()`, printed in the old order (build_flags, stop_gate, sandbox, seam, browser) and judged by the old code (`ok=1`, same messages, the browser check's exit 3 still a HOLE line). An EXIT trap waits for every job, so none outlives `fast()` on any path. `tgate` (the kit's `gate` plus seconds) wraps private_name_check, sluice_hold, license_audit and choc_patch in fast, and `gate` wraps rtsan_check, h2_engine_rtsan_check, admission_check, tsan_stress_check and conformance_check in full. `fast()` ends with `verify timings: total N s; slowest: ...` and writes `.harness/verify-timings.json`; both targets end with `verify: N gates recorded, K skipped: names`.
  - Eight tools print `KIT-GATE skipped: <reason>` on exactly the paths where they judged nothing or skipped rows (license_audit_check, choc_patch_check, private_name_check, sluice_hold_check, rtsan_check, tsan_stress_check, h2_engine_rtsan_check, admission_check). conformance_check is a binary, so its skip branch in `verify` runs `gate conformance_check echo "KIT-GATE skipped: ..."`. No exit code or other message changed.
- **Shared state, checked in the five sources (read, then confirmed by four runs):**
  - gui3_seam_check: reads the repo only; no writes, no ports, no scratch path.
  - gui3_browser_check: serves docs/ on port 0 (any free port), headless Chrome with `--remote-debugging-port=0` and a `--user-data-dir` from `mkdtemp(gui3-*)` per sub-check; spawns python only to read (gui3_inline). Writes nothing in the tree. It is the load-sensitive one (a comment cites a 300 ms read that went red under load), and it was green in all four concurrent runs here, at load average 5 to 6.
  - sandbox_check: everything under `mkdtemp(sandbox_check-*)`; it copies `tools/`, `reference/` and chosen docs into that scratch tree and runs git only inside it (`git init` in `base/repo`, with GIT_CONFIG_GLOBAL/SYSTEM=/dev/null). It copies only `.mjs/.cjs/.js/.json/.py` files, so a `__pycache__` appearing mid-copy is not copied. It does run `git ls-files` (via sandboxed_node) on the real repo, which only reads the index.
  - build_flags_check: reads files; writes the pin only on `--approve`/`--append`, which verify never passes.
  - stop_gate_check: `mkdtemp(stopgate-*)`, scratch git repos, copies kit files from the tree.
  - No two share a port, a fixed `/tmp` name, a browser profile, a tree file or the index. All five therefore ran concurrently, except that build_flags and stop_gate share ONE slot in sequence: the cap is four background jobs plus the foreground, and 22 s + 13 s is under the 56 s of the longest gate, so the chain costs nothing on the critical path. They are serial with each other for the cap, not for shared state.
  - The foreground gates were checked the same way for the index and the tree: `git status --porcelain --ignored` before and after the serial baseline run differs only by `.harness/` itself.
- **Not timed:** the ~100 other gates in `fast()` are not individually timed (wrapping each call line was a large diff for little information); the JSON has the nine gates above and `fast_total`. Seconds are whole (bash 3.2).
- **Before / after** (`nice -n 10 ./verify fast`, this worktree, no submodules, shared machine):
  - unmodified origin/main `verify`: 4:38.57 wall (278.6 s), user 279.0 s, load average 4.45 at the start and 9.34 at the end, exit 0.
  - this change: 118.7 s (load 4.45 to 6.06) and 126.4 s (5.44 to 6.20), exit 0 both. About 2.2 times faster; the longest gate (gui3_seam, 56 s alone, 75 to 82 s under contention) and the serial rest now bound it.
- **Verdicts:** the sorted output of the baseline and of the new run differ only in the new KIT-GATE lines, the timings and receipt lines, and the playbook drift notes (they cite `verify:<line>` and the line numbers moved). Every GREEN / PASS line is present in both.
- **Plants (all reverted, `cmp` against the saved script):**
  1. gui3_seam_check pointed at a nonexistent file: `verify: GUI 3 seam check FAILED` with node's "Cannot find module", exit 1.
  2. stop_gate replaced by `exit 7` (the chain's second job) and the browser check by `exit 3`: `PLANTED stop_gate` printed and verify exit 1; the browser's exit 3 printed only `verify: PLANTED browser hole` (HOLE path, not a failure).
  Plant 1 also turned test_table_check red (the plant unwires a named tool), as it should.
- **Receipt in this worktree** (no submodules): `gates` holds private_name_check ran, sluice_hold skipped ("local/sluice absent, nothing was scanned"), license_audit skipped ("rows reading libs/choc, libs/clap, libs/clap-wrapper did not run (not checked out)"), choc_patch skipped. Last line: `verify: 4 gates recorded, 3 skipped: sluice_hold, license_audit, choc_patch`.
- **Evidence consulted:** docs/audits/2026-11-10-fable-audit.md findings 4 and 8; `.kit/kit-gates.sh` 90-160 (`gate`, `record`; not edited); the five tools' sources; tools/armor_coverage_check.py (it finds a gate function by the call shape `name || ok=1`, which is why `tgate` sits inside `private_name_gate` and not at its call site; the first run of this change was red on exactly that, `armor_coverage_check: FAILED (1) ... SEC-hygiene: gate 'private_name_gate' is not run`).
- **Alternatives rejected:** five concurrent jobs (breaks the cap of four); `wait -n` to start the fifth when one ends (bash 3.2 here has none); polling for a free slot (a chain is simpler and costs nothing on the critical path); wrapping all ~100 gates in a timer (diff size); `|| true` anywhere (weakening_check counts it).
- **Verify:** `./verify fast` exit 0, 126 s, tree 31b1a658 plus this change (see .harness/last-verify.json). `./verify full` was NOT run (needs a build tree and human-paced checks); its changes are `bash -n` clean and mirror fast's `gate` use, and its skip lines are exercised only by the tools' own SKIPPED paths. That is a hypothesis, not a verified fact.
- **Open questions:** (1) the CI `verify-fast` jobs still check out no submodules (`ci.yml:67-74`), so the license and patch rows run only on the root checkout; the audit proposes `submodules: recursive`, which is out of this brief's scope. (2) The receipt now shows skipped gates; no consumer was changed to refuse a skip. (3) With one slot per chain the fifth gate cannot start earlier than the first free slot; if gui3_seam keeps growing it remains the critical path.

# b448-c3-gui-drop-guard — the GUI page refuses dropped files and links

- **Queue item:** B448 / ADR-197 Blind-Spot Armor, Phase 1 Wave C item C3 (also a B446 hardening item, the GUI web view).
- **Why:** the GUI has no drag-and-drop feature, so a file or link dropped on the web view is always stray; by default a web view may navigate to it or give the page its contents. The page now cancels all three drop events in the capture phase, the macOS view registers no drag type, and a static check plus a run-time row hold both. Defence in depth beside the navigation allowlist (ADR-196, `src/gui/embedded_page_policy.h`).
- **What changed:**
  - `src/gui/gui2.html`, `src/gui/gui.html`: `refuseDrop` plus three literal `document.addEventListener(..., true)` registrations at the top of the first inline script (before TOKEN BRIDGE / after "use strict"). Neither page had any `draggable`, `dataTransfer`, `.files` or drag handler before (grep of `src/gui/*.html`, 2026-10-09), so no existing interaction needed keeping; knobs and sliders are pointer events (`gui2.html` `k.classList.add('drag')` is a CSS class on a pointer gesture, not HTML5 drag).
  - `src/gui/hypersaw_gui.mm`: `[wk unregisterDraggedTypes]` at the end of `lockToEmbeddedPage`.
  - `tools/gui_sink_check.py`: `drop_guard_problems` (required guard, forbidden reads, `draggable="true"` unless in `DRAGGABLE_EXCEPTIONS`, empty today) and `drop_guard_controls` (planted copies of the real gui2.html, written to a temp dir).
  - `tools/gui_webview_check.mm`: DROP rows and their CONTROL rows.
- **CSP hash:** nothing stored to update. `embed_file.with_csp` hashes the inline scripts at embed time and `gui_sink_check` recomputes them; both pages' policy rows read OK after the edit. `gen_gui_controls.py --check`: GREEN (238 controls), the guard sits outside the generated regions.
- **Native findings:**
  - macOS: DONE, in our code. WKWebView registers 17 dragged types by default (`registeredDraggedTypes`, first three: NSColor pasteboard type, public.png, NSFilenamesPboardType); after `unregisterDraggedTypes` in the ready callback it reads 0 once the view is attached and the page has loaded and run (gui_webview_check DROP). Not re-asserted at attach because the count is 0 after attach. Hypothesis, unmeasured: a host that detaches and re-attaches the view could make WebKit register again; the row would not see it.
  - Windows: NOT DONE. WebView2 has `ICoreWebView2Controller4::put_AllowExternalDrop(FALSE)`, but choc keeps the controller private (`coreWebViewController`, `choc_WebView.h`) and declares only Controller and Controller2, so a guard needs a choc patch (a new option plus the Controller4 interface, in the style of `libs/patches/choc-webview2-navigation.patch`). Out of scope by the brief; the page-level guard is the Windows defence meanwhile, runtime-unverified there.
- **Run-time half (macOS):** `dropProbe` dispatches `dragenter`, `dragover`, `drop` as `DragEvent`s carrying a `DataTransfer` that holds a `File` (constructible in this WKWebView: `files` reads 1) at `#presetList`. It reads `defaultPrevented` after dispatch, `defaultPrevented` as an element-level listener sees it on arrival (proves the guard runs first, i.e. capture), and whether `location.href` is unchanged. Control: the plain choc view's page has no guard and reads all false. Plus `registeredDraggedTypes` 0 on the shipped view, 17 on the control.
  - Does NOT prove: a script-dispatched event is untrusted, so WebKit never runs the default action (navigate) with or without the guard. A real drop onto the view was not exercised. The cancelling is measured, not the drop.
  - `dropEffect` is NOT asserted: on a constructed DataTransfer WebKit pins it to `none` even on the unguarded control (measured; `effectAllowed='all'` first did not change it), so reading it would pass for the wrong reason. `effectAllowed` is not set by the page: it is the drag source's to set, in dragstart only.
  - Live mutation, once: gui2.html's drop registration changed to non-capture and rebuilt; DROP read FAIL with `"drop":{"prevented":true,"atElement":false}`; restored (byte-identical, cmp) before the final build.
- **Static limits:** the check finds `preventDefault()` in the handler's text and the three literal registrations; it does not prove the call runs on every path, and `dataTransfer` aliasing (`const d = ev.dataTransfer; d.files`) is not followed. The guard itself uses `ev.dataTransfer`, so a bare `dataTransfer` mention is allowed. The run-time row is the cover for the first; the second is a stated gap.
- **Evidence consulted:** `src/gui/{gui2.html,gui.html,hypersaw_gui.mm,hypersaw_gui_win.cpp,embedded_page_policy.h}`, `tools/{gui_sink_check.py,gui_webview_check.mm,embed_file.py,gen_gui_controls.py}`, `libs/choc/choc/gui/choc_WebView.h`, `verify` (gui_sink_check in fast, gui_webview_check in full).
- **Alternatives rejected:**
  - A new tool for the static check: gui_sink_check already owns the page scan and the planted-control pattern.
  - Asserting `dropEffect`: a detector that reads the same on the control.
  - A loop over the three event names in the page: unreadable to the scan and no shorter.
  - Re-calling `unregisterDraggedTypes` at attach: the count is already 0 after attach.
- **Not covered:** the lab pages in `docs/design/` are not shipped and not scanned. Three of them (`envelope-hierarchy-lab.html`, `maw-horde-lab.html`, `scalpel-interface-lab.html`) mention drag or drop handlers of their own, so a blanket guard would break them; none would benefit.
- **Verify:** see the PR; `./verify fast` result recorded from `.harness/last-verify.json` there and in the report.
- **Open questions:** (1) A choc patch for Windows `put_AllowExternalDrop` is the human's call. (2) Whether the macOS drag-type count survives a host that re-parents the view is unmeasured.

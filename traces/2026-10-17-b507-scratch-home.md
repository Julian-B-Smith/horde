# b507-scratch-home — store-touching oracles run under a scratch HOME in ./verify

- **Queue item:** ROADMAP B507 (approved by the human 2026-10-17, ADR-237 item 11). Editing `./verify` is a human gate; this edit was approved for exactly this scope.
- **Why:** `trace_check` and `endprobe` press PANIC, which writes `$HOME/<store>/logs/panic-<n>.txt` (`src/hypersaw_clap.cpp` writeForensics, through `presetRoot()`); the serial `./verify` ran them with the real HOME, so test dumps landed in the developer's real preset store. B505 had already given each oracle its own HOME under the CI sanitizer (`tools/sanitize_oracles.sh`); `./verify` did not.
- **What changed:** `verify`: a function `in_scratch_home` (fresh `mktemp -d` as HOME, `$box/tmp` as TMPDIR, removed after, exit code passed through); `trace_check` and `endprobe` run through it; `fast()` runs the new `tools/store_logs_check.py`; the `fast` and `full` dispatcher arms bracket the run with `store_logs_check.py snapshot|compare` of the REAL store's logs/. New `tools/store_logs_check.py` (wired in `./verify fast`, header `WIRED:`). No oracle's logic or arguments changed.
- **Store-touching oracles found.** Static (sources calling `hypersaw_test_panic` / `hypersaw_test_dump_forensics` / `panicWithDump`): `tools/trace_check.cpp:142,307,324`, `tools/endprobe.cpp:83`, `tools/identity_store_check.mm:240`, `tools/rtsan_probe.cpp:625`, `tools/tsan_stress.cpp:311`. Dynamic (every plugin-linked oracle ./verify runs directly, run once under a scratch HOME and the HOME listed afterwards): only `trace_check` (8 files in logs/) and `endprobe` (1 file) write under HOME. Already isolated before this change: `identity_store_check` and `gui_webview_check` (setenv HOME inside the binary), `presetstore_check` and `preset_pitch_check` (setEnv HOME), `rtsan_probe` and `tsan_stress` (their python drivers `tools/rtsan_check.py:214-219` and `tools/tsan_stress_check.py:195-200` redirect HOME). The survey skipped the heavy h2 core oracles (core-only, not linked to the plugin: `h2_engine_*`, `h2_scalpel_*`, `stability_check`) and the golden-parity checks whose goldens were absent in the survey (no panic or store hook in their sources).
- **Evidence consulted:** `verify` (whole), `tools/sanitize_oracles.sh:185-240`, `src/gui/preset_store.h:59-85`, `src/hypersaw_clap.cpp:2258-2275`, `tools/test_table_check.py` (WIRED header rule), `docs/` not needed.
- **Alternatives rejected:** wrapping every compiled oracle (a bigger diff to change nothing: only two write there; a future one is caught by the before/after bracket, whose red names the file). A hard-coded oracle list in the check (a second list drifts, L0005): the list is derived from the oracle sources, with a two-name floor so a drifted regex reads red. Wrapping `./verify` as a whole in one scratch HOME (it would hide the bug rather than catch it, and the GUI oracles set their own HOME).
- **Verify:** `./verify fast` exit 0 on the tree with `verify` and `tools/store_logs_check.py` (git 67ce957 base). `./verify full` exit 0 on the same tree (tree 75210df556f6db91fcb34d1db2d10f0032c2d1b6): `trace_check: GREEN (0 failures)` and `endprobe: PASS` ran under the scratch HOME, so `trace_check` still reads its own dump; the real store's logs/ held 8 files before and after both runs. Controls (fake HOME laid out like the store): a planted new file reads red (rc 1, `NEW HYPERSAW/logs/panic-99.txt`), an overwritten dump reads red, an untouched store reads green, `./verify`'s own `in_scratch_home` leaves the fake store unchanged while the same child without it changes it, and `./verify` with `endprobe` unwrapped reads red.
- **Open questions:** (1) a real DAW or a hand-pressed PANIC during a run reads as a leak (false red, never a miss); the check's header says to re-run with the host closed. (2) `nightly` is not bracketed (it `exec`s `tools/nightly/run.py`; out of scope). (3) The 8 existing dumps in the real store (panic-0, 8, 9, 10, 1810, 1823, 1921, 1923) were not deleted; which are test dumps and which are the human's is theirs to say.
